# FUN_18002ba60

  `6673db3874fea66a58e2da29e371d797b890c767ba0491134d4a372c5b27e3b4`.
- Entry/body: `0x18002ba60..0x18002bbe2`.
- Caller: `_CheckIdentifyUpdate_Unify` (`FUN_180031510`).
- Callees: exported `templateStudy`, exported `templateGetPackedSize`, and

- Role: transfer the successful-match latch, run study, and compute either the

## Questions

- Under which recognition/update conditions is study invoked?
- How is its update result consumed by the adapter?

## Audit Findings

- The adapter invokes `templateStudy` only after its successful-match flag is
  set by image identification.
- The successful-match flag is global byte `0x18019b9b4`; the wrapper copies it
  to its caller output and calls `templateStudy(&0x18019c170)` only when the
  byte is exactly `1` (`0x18002baaa..0x18002baba`).
- A positive update causes the matched template to be repacked at its new size;
  a zero update preserves the prior serialized size.
- Specifically, update `<= 0` returns the preexisting packed-size value from
  global `0x18019b9f8`; update `> 0` calls `templateGetPackedSize` for the
  matched candidate and adds the adapter's `0x34`-byte wrapper. The wrapper
  then clears the successful-match flag after copying it to `0x18019b9b5`.
- The oracle calls study after `identifyImage` returns status zero with a
  positive score, which corresponds to the observed successful-match case.
- A replay that persists only the post-`identifyImage` template while skipping
  `templateStudy` is therefore a diagnostic match-mutation model, not a
  production adapter mode. Production successful matches enter study.
- Downstream `_CheckIdentifyUpdate_Unify` (`FUN_180031510`) and
  `_CheckUpdateTemplate_E` (`FUN_18002bbf0`) pack and replace the WBF storage
  record only when this function's study update is positive. Update code zero
  retains the prior persistent template even if the in-memory match snapshot
  changed.

## Code-3 Caller Correction

The comparison is signed `update < 1`; therefore 3 follows the same new-size
path as 1, 2, 4, and 5. It is not filtered or remapped. Direct export controls
show `templateStudy` returns status zero/update 3, after which this helper
computes the matched handle's new packed size. The successful-match latch is
then transferred and cleared exactly as for observed positive actions.

## Action-0 Size And Authentication Boundary

Unit-5 call traps confirm the assembly split at
`0x18002babf..0x18002bb5b`. Every action-0 family takes signed update `<=0`,
loads the prior serialized record size from `0x18019b9f8`, and adds only the
adapter overhead. It never calls `templateGetPackedSize` at `0x18002bade`.
The positive action-1 sanity control reaches that address exactly once.

The successful-match latch at `0x18019b9b4` is a separate earlier boundary. If
zero, this helper does not call `templateStudy`, leaves the retained probe
unconsumed by study, requests no update size, and transfers match status zero.
If one but shared evidence `+0x688` is zero, `templateStudy` is called and
consumes the probe but skips its dispatcher. These two update-0 families must not
be conflated. Evidence is in `study-action0-finalization-unit5-v1`; confidence is
high.

Native unit 5 preserves this split: transient diagnostics do not enter the
`updated_feature` output, so action 0 has no native size-query analogue. The
positive action-1 sanity still produces exactly one update candidate.
