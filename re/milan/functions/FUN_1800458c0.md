## Recovered Behavior

The helper copies bounded records through `FUN_180037690`, updates feature maps
and relation state, clones the derived mask and quality/coverage fields, and
deep-copies the `0x1abc` anti-fake object when present. Unlike the append helper,
it targets an existing feature slot and participates only in the full-capacity
replacement family.

The record bound is the live template maximum passed as the third argument to
`FUN_180037690`. At `0x1800376f8..0x180037732`, a probe at or below that bound is
copied completely and carries its partition boundary `b7/+0x118`. Above the
bound, `0x180037737..0x1800377ec` ranks records by their live `+0x08` word through
`thunk_FUN_18006ee50` (`0x18006eed0`), copies only the bounded winners, and calls
`FUN_180037480` to repartition them and regenerate `b7`. The type-12 clearing of
live record spans follows at `0x180037809..0x180037843`; those spans are absent
from the 32-byte packed record form.

This ranking/truncation branch is real but not a packed-64 replacement contract.
Successful profile-9 unpack normalizes the effective record capacity to 150
before this call, so a packed probe declaring 64 records is copied under the
150-record bound rather than truncated to 64. Packed-64-driven truncation is
therefore refuted and requires no production change. Admission of non-150 or
unequal record-capacity metadata remains deferred: the DLL permits unequal
fields and supplies no safe finite domain from which a stricter generic rule can
be derived.

Its `FUN_1800452e0` call preserves the selected feature's `b6` row base and, when
the selected feature is not the live reference, resets every incident matrix
slot to the unset identity sentinel. The caller later invokes `FUN_180045d40`
for update code 4 to install the selected relation to the reference. This is why
the frozen replacement transitions retain star cardinality while changing one
serialized slot.

The caller has two distinct replacement mutations. Evidence flag one uses
direct action 4, copies the matched feature's `be`, invokes this helper, and
installs the selected reference relation. Evidence flag zero uses action 2 only
when probe coverage is at least matched coverage minus 10, invokes this helper,
then clears selected `b5` without the action-4 relation install. Code 2 is
statically controlled but absent from all 798 corrected natural rows.

The replacement copy boundary is intentionally selective. It copies probe
quality/coverage at `+0x11c/+0x120`, conditionally copies probe `c0` at `+0x14c`,
and never reads or writes optional `c7` at `+0x150`. Because it mutates an
existing preallocated target, target `c7` is preserved for actions 2, 3, and 4;
probe `c7` is not imported.

The exact `c0` condition is at `0x18004594e..0x180045961`: copy probe `c0` only
when it is nonzero and odd; otherwise leave target `c0` unchanged. This is
neither unconditional probe ownership nor unconditional target ownership.
Current `drivers/goodix53x5/milan/study/study.c` reconstructs the target from the
probe prefix and then always patches tag `c0` back to the old target value. It is
therefore exact for the ordinary zero-probe case but wrong for every valid odd,
nonzero probe `c0`. The minimal generic correction is to select probe `c0` when
`probe_c0 != 0 && (probe_c0 & 1) != 0`, otherwise target `c0`; no row, action, or
feature-index special case is involved.

A synthetic-valid control seeded from verify operation 101 held the action-4
target at feature 22 with target `c0=42` and changed only probe `c0` across 0, 2,
and 3. Current `goodix_milan_study_replace()` packed `42, 42, 42`; direct calls to
the approved DLL helper packed `42, 42, 3`, matching the recovered zero/even/odd
branches. The DLL's live `+0x14c` values and repacked `c0` bytes agreed in every
case, so the odd-nonzero mismatch is not a decompiler-only inference.

Natural profile-9 extraction does not currently reach that mismatching branch.
Both production DLL export callers pass a null auxiliary input to
`FUN_18004ae70`, which writes probe `+0x14c=0`; current extraction likewise
zero-initializes the tagged fields and never assigns packed `c0`. All 334 probes
in the frozen expanded corpus and all 1,286 readable probes across the retained
campaigns have `c0=0`. The generic correction remains necessary for valid
externally supplied or future-produced odd values, but it does not explain a
current natural campaign row.

Production commit `fa4aac3` implements the recovered conditional ownership.
The controlled zero/even/odd witness is byte-exact to the DLL at `42,42,3`.
Fresh current-schema validation passes the independent 450- and 643-operation
campaigns, 1,093/1,093 unique selected operations total.

The nested `FUN_1800452e0` call also applies target-owned lifecycle state before
the explicit probe copies. In particular, nonzero tag `ba` at live `+0x124` is
promoted to 2 while zero remains zero. This resolves the previously separate
native/official `1/2` byte on replacement feature 39.

Replacement counter mutation begins inside `FUN_1800452e0` before its optional
matrix allocation: template `+0x8cf8` and target tag `bd`/live `+0x130` are each
incremented with one unchecked 32-bit `INC` at `0x180045310` and `0x180045316`.
Both wrap modulo `2^32`; target `bd == INT32_MAX` becomes `INT32_MIN`. The same
shared helper accepts arbitrary signed old `bc`, wraps decrements of greater
ordinals, and rewrites the target to `feature_count-1`; old `bc=-1` therefore
produces target `bc=39` at profile-9 capacity. Production commit `a29d5d5f`
implements these rules with defined unsigned arithmetic and signed
reinterpretation.

The DLL helpers are void and mutate the live gallery in place. Allocations in
the record, optional matrix, and anti-fake copy paths are not checked before the
returned pointer is stored or consumed; there is no recoverable mutation status
or rollback. A late allocation failure can therefore occur after the two counter
increments and other target writes, normally as a process fault rather than a
clean action-zero result. The native implementation's unpacked working copy,
checked allocations, and no-publication-on-pack-failure behavior are an
intentional safety improvement and must not be changed to reproduce that unsafe
failure mode. It does mean allocation-failure parity cannot be claimed from
successful replacement rows.

Native tentative action/index publication after the copier returns is real: an
injected late failure can leave nonzero diagnostic outputs with no packed
candidate. The copier's recoverable failure requires injected null state that is
not reachable from valid or synthetic-valid template transactions. Production
callers publish no template on the error and discard the diagnostics, so this
remains a validated no-change boundary rather than a reason to alter successful
publication timing.
