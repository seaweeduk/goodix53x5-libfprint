# FUN_18002c810

## Audit Scope

Production adapter caller of `preprocessor` at `0x180002ab0`. This note was
created before first Ghidra inspection during the independent methodology audit.

## Questions

- What are the seven production arguments for enrollment and identification?
- Which purpose, liveness, and mode values are used?

## Audit Findings

- Identification passes purpose `0`, liveness `0`, and the caller-provided mode
  byte as the seventh `preprocessor` argument.
- Profile-9 enrollment passes purpose `1`, liveness `0`, and mode `0`.
- On successful preprocessing the adapter snapshots the calibration workspace,
  raw frame, and three sensor metadata values for enrollment/identification.
- The corrected oracle preprocesses enrollment replay with purpose `1`,
  liveness `0`, and mode `0`; identify-only replay uses purpose `0`.
- Purpose is also stored in both image descriptors, so artifact consumers can
  reject captures made with the wrong operation purpose.

## Profile-9/Type-12 Generation Audit (2026-08-04)

- Ghidra independently confirms two production `preprocessor` calls in this
  wrapper: enrollment at `0x18002cd7b`, after stack purpose is set to `1` and
  mode/liveness bytes are set to zero at `0x18002cd4a..0x18002cd4f`; identify at
  `0x18002cf3a`, after purpose is set to `0` at `0x18002cefa`, liveness is set to
  zero at `0x18002cf0e`, and the caller mode byte is copied at
  `0x18002cf02..0x18002cf0a`.
- A direct approved-DLL generation control executed preprocessing in order
  identify `0`, enroll `1`, identify `0`. Its target processed SHA-256 is
  `bd1f99a908bbc473745d001597e237ba3b286e1b7077f3c475058ab9657db9f4`;
  target quality/coverage is `90/100`, status is zero, and the complete target
  result is byte-identical to the purpose control `0/0/0`. A fresh target with
  no two-call prelude differs at processed SHA-256
  `2ceb1c407d42ac99df4b370252e7157d8450c8ed20a7dc0a95006434b4a31072`
  and quality `89`, demonstrating retained generation history while isolating
  no purpose-dependent difference for these controlled frames.
- This equality is profile-gated, not permission to erase purpose. Profile 9
  fixes packed subtype `12` and its configuration field 7 to zero; the
  purpose-1 threshold arm at `FUN_18006c510:0x18006c747..0x18006c766` requires
  field 7 equal to 2 and belongs to another profile configuration.
- Confidence is high for production purpose provenance and retention across one
  mixed-purpose generation. The control demonstrates these three frames only;
  it does not claim purpose equivalence for other profiles or configurations.

## Cancellation And State Ownership Audit (2026-08-08)

- `WbioQueryEngineInterface` returns the engine table at `0x1800f2290`.
  Its `AcceptSampleData` entry is `FUN_18001c5f0`, which calls
  `FUN_18001f610 -> FUN_180032040 -> FUN_18002c810 -> preprocessor`
  synchronously. No function in that path accepts or checks an operation
  cancellation token.
- The engine interface exports no operation-cancellation entry. Clear-context
  (`FUN_18001f090 -> FUN_180031330 -> FUN_18002b960`) finishes enrollment and
  frees adapter-owned buffers, but it does not restore a pre-call preprocessing
  snapshot. Detach is a lifecycle teardown, not an operation rollback.
- `FUN_18002c810` calls `preprocessor` directly against the DLL's persistent
  process globals and has no rollback branch after the call. A frame that
  reaches preprocessing therefore retains its native state mutations even if
  the Windows host later abandons the surrounding operation.
- This does not match the Linux runtime's deliberate `GCancellable` policy,
  which clears `preprocess_state_valid` and discards its copied generation state
  when cancellation is observed at a runtime checkpoint. Parity preludes
  reconstruct the state Linux actually committed before a later selected
  operation; they are not a replay of a cancelled Windows operation. A
  runtime-observed cancellation therefore consumes its generation-use position
  but supplies no frame. A driver-only late cancellation supplies its frame
  because Linux committed preprocessing state before observing cancellation.
- Cancelled operations remain unavailable as selected native-runner targets
  because the DLL exposes no natural cancellation operation to replay. The
  current validator enforces those ownership rules without changing runtime v3.
  The unchanged 701-record campaign contains no cancellation evidence and still
  passes 643/643 selected operations; a new durable campaign should directly
  capture cancellation before this edge is considered naturally covered.
