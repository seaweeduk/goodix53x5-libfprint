# FUN_180032040

## Identity and inputs

`GoodixEngineAdapter.dll!0x180032040`, `_PreProcessor_Unify`, calls the
production preprocessing adapter wrapper `FUN_18002c810` from sample acceptance
in `FUN_18001f610`.

- Engine context `+0x198` is passed as wrapper argument 3 and becomes exported
  `preprocessor` argument 3, the optional `0x4c98` auxiliary object.
- Engine context `+0x190` is passed as wrapper argument 4; it is required
  nonnull but is not the feature auxiliary.
- The wrapper derives exported purpose internally: identify `0`, enrol `1`.
- Context bytes `+0x1b4`, `+0x1b5`, and `+0x1b6` become retained `tCode`,
  `dacHigh`, and `dacLow` respectively.
- Context `+0x94` is not used here; the fifth caller argument becomes the
  exported mode switch. At `0x18002004a`, the normal sample-accept path writes
  `0` to that stack argument immediately before calling this function, so both
  production identify and enrol preprocessing use mode `0` on this path.

## DAC metadata consumer

`usbinterface.dll` publishes the post-successful-read 16-bit DAC in the sample
trailer. The overlapping copies in `FUN_18001f610` leave its low byte at context
`+0x1b5`; this function forwards that byte. See
`usbinterface-FUN_18001fb40.md` for trailer layout and
`usbinterface-FUN_180007c84.md` for the adjustment producer.

At `0x1800321c9/0x1800321d9/0x1800321e9`, `MOVZX` reads one byte for
`dacLow/dacHigh/tCode`; the corresponding outgoing stack stores are also
one byte. The current adapter boundary is
`drivers/goodix53x5/milan/runtime.c:goodix_milan_runtime_build_probe`, which
projects all three words to `guint8` before `goodix_milan_match_extract_native`.
`goodix_milan_runtime_input_new` and `goodix_milan_runtime_output_new` retain
the acquisition words. The lower extraction/anti-fake APIs retain their word
arguments; byte projection belongs to this sample-adapter boundary.

The triplet is not an argument to the image-rendering `preprocessor` export.
`FUN_18002c810` calls that export at `0x18002cd7b` or `0x18002cf3a` before
reading the triplet's incoming stack slots. After nonzero quality and coverage,
`0x18002d048..0x18002d06e` zero-extends the three bytes into words at
`0x18019c180/+2/+4`, alongside the copied calibration workspace at `+6`.
Thus changing only these metadata bytes, with identical raw image and entry
workspace, does not change that invocation's rendered image or its metrics.

The retained triplet instead reaches `enrolAddImage`/`identifyImage` through
`FUN_18002d4b0`/`FUN_18002e360`. Their type-12 residual offset is
`s32(u32((dacHigh-dacLow)*tCode*283))/1000`, with signed division toward zero.
`FUN_1800392f0` passes it to `FUN_18003a150` for the anti-fake residual,
separately from the processed-image renderer; see those owning notes. Current
source splits these consumers between `milan/runtime.c`,
`milan/match/info.c`, and
`milan/antifake/construction.c:milan_antifake_sensor_offset`.

For fixed raw/calibration pixels, `FUN_18003a150` writes the low word of
`calibration-raw-sensor_offset-0x1bb7` at each interior pixel and extends the
border for type 12. The later `FUN_180039fc0` publishes the masked residual
mean as well as a separate high-pass texture statistic. High-pass centering
therefore does not remove the absolute residual mean from the anti-fake
object. These consumers do not feed DAC changes back into an already acquired
raw frame.

In `identifyImage`, the extraction call at `0x180001c8a` receives the processed
image, quality/coverage, candidate configuration and auxiliary workspace, but
none of the calibration triplet. The three word loads and offset arithmetic
begin only after extraction succeeds, at `0x180001cbc..0x180001d2f`, and feed
the anti-fake call at `0x180001dd3`. Thus the triplet is not an input to that
call's extraction-classification history update. The anti-fake builder clears
and rebuilds the complete per-feature object for the current image, including
when its allocation survives a preceding no-match; see `identifyImage.md` and
`FUN_1800392f0.md`. An earlier image's anti-fake contents can survive in gallery
or study-owned features, but are not an accumulated calibration input to the
next live image's anti-fake construction.
