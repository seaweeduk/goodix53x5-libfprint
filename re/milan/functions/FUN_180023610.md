## Recovered Behavior

After validating the engine object and its transfer state at object `+0x38`,
the function deactivates the operation and unconditionally enters
`FUN_180031510`. That worker itself checks the successful-match latch and the
study update result. Therefore the externally visible scheduling boundary is
deactivation, while actual packing and storage replacement remain gated by a
successful identify and update code greater than zero.

## Deactivation Error Ownership

For a non-null pipeline with non-null engine context at `+0x38`, this entry
calls `FUN_18001e230(pipeline, 0)`, discards its return, calls
`FUN_180031510(pipeline)`, discards that return too, and returns zero. Only the
null pipeline/context checks set its return to `0x80004003`. The match/update
worker is therefore reached even when the deactivation IOCTL fails; transport
success is not an additional study or storage-admission predicate.

`FUN_18001e230` (`_AdapterActivate`) sends IOCTL `0x442020` with one input
byte (zero for deactivate), a one-byte output, and an event-backed OVERLAPPED.
Pending I/O (`GetLastError() == 997`) is completed using blocking
`GetOverlappedResult(..., TRUE)`. Successful completion with one returned byte
copies that byte to engine context `+0x1b7` (broken-study flag). Failed I/O or
a non-one-byte result returns `GetLastError()` and does not replace that flag.
This helper neither clears the match latch nor removes an existing update.
Its event is closed before return.

The corresponding USB `OnActivate` handler (`usbinterface.dll`,
`0x1800214d0`) itself ignores the mode-2 sleep result and completes its
activation request successfully. Thus exhausted sleep ACK attempts do not
become a failed engine deactivation result; a direct IOCTL failure is a
separate outcome that this engine entry also ignores.

`EngineAdapterVerifyFeatureSet` (`0x180020600`) returns its comparison result
and match byte from engine context `+0x11c`; it does not call this deactivation
entry. Update/storage work occurs when deactivation is subsequently invoked,
not before its IOCTL: `FUN_180031510` checks the successful-match/update
predicates, performs eligible replacement, and finally clears `+0x11c`.
See `FUN_180031510.md` for the independent storage-result gates.

## Rare-Action Consequence

Deactivation does not filter update identity. Exported code 3 reaches
`FUN_180031510`, which packs on positive action and schedules delete/add storage
replacement. A queued follow-up can instead expose 5; it follows the same
positive path.
