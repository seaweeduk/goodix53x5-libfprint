## Recovered Behavior

It computes centered horizontal/vertical gradients from a 32-bit extraction
plane, clamps each component to signed 19 bits, derives orientation with
`FUN_180074290`, and stores magnitude plus orientation planes used by descriptor
construction. It does not decide the sequence-72 record count.

For type 12, `FUN_180049b90` produces that input as
`10*Gaussian_0(enhanced<<8) - 9*Gaussian_1(Gaussian_0(...))` on the first pass,
or the corresponding IDs `100/101` on retry. All arithmetic in that combination
is signed 32-bit and is in range because both filter outputs are unsigned 16
bits. Successful current filtering uses the same expression at
`feature/extraction.c:234..240`.

Only pixels with `1 <= x < width-1` and `1 <= y < height-1` are written; caller
zero-initialization leaves the one-pixel border zero. Each component is clamped
to `[-0x80000, 0x7ffff]`, shifted left 12 in a 32-bit lane, and passed as
`FUN_180074290(&vertical, &horizontal)`. The returned low 16-bit angle is stored
in the signed orientation plane. The helper replaces horizontal with rounded
CORDIC magnitude; this function arithmetic-shifts it back 12 and caps only the
upper result at `0x3ffff` before a 32-bit store. Current source correspondence is
`drivers/goodix53x5/milan/feature/extraction.c:207-273`; the anti-fake variant
without the extraction filters is `antifake/feature.c:47-66`.

A focused full-kernel bound closes the prior CORDIC endpoint question. For an
arbitrary production-sized byte image, adversarial binary inputs attain raw
horizontal differences `+/-155858` with IDs `0/1` and `+/-159465` with IDs
`100/101`; the exact linear upper bounds plus all per-filter truncation error
remain below `160000`. Vertical bounds are identical by separability. Thus the
`[-0x80000,0x7ffff]` clamps cannot activate on profile-9/type-12 production
inputs, and the following `<<12` cannot supply `INT32_MIN` to `FUN_180074290`.
The clamps remain part of the exact generic native contract for independently
supplied 32-bit planes.
