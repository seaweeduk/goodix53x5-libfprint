## Recovered Behavior

It independently partitions the primary record array at `+0xf8` and optional
secondary array at `+0x100`. Counts are signed 32-bit live fields and each record
is exactly `0x38` bytes. A two-ended scan advances the left index only while
`record[0] & 3 == 0`, retreats the right index only while
`record[0] & 3 == 1`, and swaps the complete 56-byte records when the indices
still differ. It writes the resulting half-open primary boundary to `+0x118`
and the secondary boundary to `+0x10c`.

The operation is an unstable partition: it preserves neither class's input
order. Zero records produce boundary zero without dereferencing the record
pointer. One record produces boundary one exactly for low class zero and zero
otherwise. All-zero and all-one arrays produce `record_count` and zero
respectively. Profile-9/type-12 materialization reaches the inline rank/copy
branch in `FUN_180049b90`, not `FUN_18004a6d0`, and naturally supplies only
Boolean values zero or one. The partition leaf nevertheless accepts any 16-bit
value congruent to zero or one modulo four because the upper fourteen bits are
ignored for classification and preserved by whole-record swaps. Such values are
synthetic-valid intermediates for this leaf, not natural type-12 extraction.

The exact post-partition physical sequence, not pre-partition strength order, is
the canonical live and packed output. For record IDs `[0,1,2,3,4,5]` with
Boolean classes `[1,0,1,0,0,1]`, the two end swaps produce
`[4,1,3,2,0,5]` and boundary `3`. Current source produces the same unstable
permutation.

Low-two-bit values 2 and 3 are not additional valid partitions. One such value
can be displaced incidentally, but two unresolved values can be swapped forever
because neither scan index advances. The DLL does not reject this state. The
profile-9 extraction path cannot produce it because its materializer writes only
the Boolean values zero and one.

Evidence is the full leaf body: primary scan/final count
`0x180037491..0x1800374f9`, primary swaps `0x18003756d..0x1800375f0`, secondary
scan/final count `0x18003750d..0x180037564`, and secondary swaps
`0x1800375f5..0x18003768a`.

Current source implements the same low-two-bit scan and whole-record swaps in
`goodix_milan_feature_partition_records()` at
`drivers/goodix53x5/milan/feature/record.c:63-90`. It deliberately returns zero
for a null pointer or empty `size_t` count, whereas the DLL is safe only for the
empty live-object case; a positive count with a null record pointer faults.
Current extraction is bounded to 150 records, so source index multiplication and
the DLL's signed count arithmetic are both safe.

Current source writes the same Boolean type-12 field in
`feature_finish_pretransform_records()`
(`drivers/goodix53x5/milan/feature/materialization.c:571-614`). There is no
profile-9/type-12 live-record representation difference at this boundary.
