# FUN_18001f610

## Audit Scope

Sample-accept path that populates engine-context bytes `+0x1b4..+0x1b7` before
calling the documented preprocessing wrapper chain. This note was created
before first Ghidra decompilation during the scoped production argument
provenance audit.

## Questions

- At which incoming sample-buffer offset are `tCode`, `dacHigh`, and `dacLow`
  stored?
- Is the fourth copied byte consumed by enrollment or identification?

## Audit Findings

- The capture image payload begins at local `sample + 0x38`.
- The payload control byte at offset `+0x00` is the hardware module's one-shot
  base-refresh marker. The live frame begins at `+0x03`; a separate full-size
  16-bit image base begins at `+0xebf0`.
- The function copies the image base into a temporary `rows * columns * 2`
  allocation and calls `FUN_180031d00` at `0x18001fef2` when engine-context
  initialization byte `+0x7c` is zero or the payload refresh marker is `1`.
- If that bridge returns a failing HRESULT, this function maps the sample to
  `0x80098008` and writes reject detail `10` at
  `0x18001fef7..0x18001ff54`. It exits before live preprocessing, extraction, or
  enrollment/identify consumption. A zero bridge result with context `+0x7c`
  still clear receives the same status and detail at
  `0x18001ff5e..0x18001ffbd`.
- A normal sample after successful initialization reuses the existing
  preprocessor calibration state. It does not call `preprocessor_init` again,
  even though the same retained image base remains present in the sample.
- The refresh decision is at `0x18001fec0..0x18001fed0`. The context's separate
  `+0x98` value is passed onward as `needupdatecali`, but it is not the decision
  that reaches this branch.
- Three little-endian 16-bit words are read at image-payload offsets
  `+0x1d7e8`, `+0x1d7ea`, and `+0x1d7ec`.
- The words are logged as `tcode_use`, `dac_h`, and `dac_l`. Overlapping
  two-byte copies retain their low bytes at engine context `+0x1b4..+0x1b6`.
- The fourth byte at `+0x1b7` is the high byte of the final `dac_l` word and is
  not forwarded to `enrolAddImage` or `identifyImage`.
- `WbioQueryEngineInterface` publishes this function in the
  `EngineAdapterAcceptSampleData` slot of the version-3 engine interface. The
  immediately following operation callbacks are `FUN_180020350`,
  `FUN_180020600`, and `FUN_180020b30`, with `FUN_180020b30` serving
  `EngineAdapterIdentifyFeatureSet`.

## Reference Provenance

- `usbinterface.dll` `CaptureFramedone` (`0x18001fb40`) serializes its second
  argument into this `+0xebf0` image-base slot.
- The hardware callback dispatcher supplies its retained image base from
  hardware context `+0x248`. `usbinterface.dll` `FUN_180015c60` proves that
  field is the first, TX-on member of a validated TX-on/TX-off low-DAC pair.
- Thus the production profile-9 setup frame reaching `preprocessor_init` is
  TX-on, not TX-off. The TX-off acquisition is not serialized to the engine.
- `EngineAdapterClearContext` (`FUN_18001f090`) can run between biometric
  operations without clearing initialized byte `+0x7c` or the preprocessor
  calibration workspace. A second probe therefore reuses preprocessing unless
  this sample's hardware refresh marker is one or the adapter is detached.
