# FUN_18001f610

## Identity

- Binary: `GoodixEngineAdapter.dll`.
- Address: `0x18001f610`.
- Role: accept a delivered sample, initialize preprocessing when required, and
  populate engine-context capture parameters before live preprocessing.

## Contract

- The capture image payload begins at local `sample + 0x38`.
- The payload control byte at offset `+0x00` is the hardware module's one-shot
  base-refresh marker. The live frame begins at `+0x03`; a separate full-size
  16-bit image base begins at `+0xebf0`.
- The adapter allocates two frame lengths for live input and copies one frame
  from payload `+3`, then another from `+3 + frame_length`. For the ordinary
  type-12 16-bit sample, each length is `0x4a40`. It retains an owned copy of the
  entire supplied sample separately at context `+0x38/+0x40`.
- The frame-length producer at `0x18001f88e..0x18001f8f9` computes
  `bytes_per_pixel = (bits_per_pixel >> 3) + ((bits_per_pixel & 7) != 0)`,
  then multiplies the two 16-bit sample dimensions by that byte count.
  `usbinterface.dll:0x180021978` supplies bits-per-pixel 16 at staging
  `0x180084902` and the profile dimensions at `0x18008490c/+2`, giving
  `88 * 108 * 2`. The remainder predicate alone is not the byte count.
- The ordinary live call passes the beginning of that allocation once to
  `FUN_180032040`, whose `FUN_18002c810` callee copies only context `+0x80`
  bytes into its input image descriptor. This length must equal the selected
  profile's `rows * columns * 2`, or `0x4a40` for type 12, and be below `0x75f9`.
  Successful setup through `FUN_180031d00` installs that supplied length at
  context `+0x80` along with its initialized-byte result.
  Neither wrapper iterates over the second live frame or advances the live
  pointer. Thus two successful USB enrollment reads yield one preprocessing
  call and at most one subsequent sample-quality/enrollment admission, not two
  stages. A one-frame remainder publication likewise supplies its new first
  frame; the copied stale second span is not an ordinary preprocessing input.
  This does not eliminate the second read's calibration effect: its successful
  dynamic-DAC adjustment precedes the trailer copy, so the first image is paired
  with the post-read DAC metadata described below.
  See `usbinterface-FUN_180014e10.md` for unread-count ownership and
  `usbinterface-FUN_18001fb40.md` for the fixed-size sample copy.
- The function copies the image base into a temporary `rows * columns * 2`
  allocation and calls `FUN_180031d00` at `0x18001fef2` when engine-context
  initialization byte `+0x7c` is zero or the payload refresh marker is `1`.
- If that bridge returns a failing HRESULT, this function maps the sample to
  `0x80098008` and writes reject detail `10` at
  `0x18001fef7..0x18001ff54`. It exits before live preprocessing, extraction, or
  enrollment/identify consumption. A zero bridge result with context `+0x7c`
  still clear receives the same status and detail at
  `0x18001ff5e..0x18001ffbd`.
- A normal sample after successful initialization reuses the existing
  preprocessor calibration state. It does not call `preprocessor_init` again,
  even though the same retained image base remains present in the sample.
- Normal live preprocessing calls `FUN_180032040` at `0x180020068`. A nonzero
  adapter status at `0x180020071` skips quality judgment and is mapped at
  `0x1800200bc..0x1800200d2` to `0x80098008` with reject detail `10`.
  Consequently profile-9 severe preprocessing reaches this complete boundary
  as raw enrollment status `0xc351` or identify status `0x80`, while the
  adjacent early-admission result reaches it as raw enrollment status `0x29aa`
  or identify status `0x80`; all four produce the same HRESULT and detail.
  The preprocessing call has already retained any state and processed output
  it completed before this mapping, and this function does not roll them back.
- The refresh decision is at `0x18001fec0..0x18001fed0`. Payload byte zero is
  zero-extended into local dword `stack +0x8c` at `0x18001fb5d..0x18001fb6f`
  and copied to context dword `+0x98` at `0x18001fbde..0x18001fbea`. The setup
  branch tests the local copy for exact equality to one, or initialized byte
  `+0x7c` for zero. The context copy is forwarded as `needupdatecali`; it is
  not an independently produced refresh condition.
- After successful setup, a live-preprocessing retry does not undo setup or
  clear initialized byte `+0x7c`. A subsequent unmarked sample therefore skips
  the setup bridge even when the marked sample did not reach extraction.
  If setup itself fails after prior initialization, the bridge also leaves
  `+0x7c` unchanged; its failure is returned before live preprocessing. See
  `FUN_180031d00.md` for that failure's calibration-ready state.
- Three little-endian 16-bit words are read at image-payload offsets
  `+0x1d7e8`, `+0x1d7ea`, and `+0x1d7ec`.
- The words are logged as `tcode_use`, `dac_h`, and `dac_l`. Overlapping
  two-byte copies retain their low bytes at engine context `+0x1b4..+0x1b6`.
- The fourth byte at `+0x1b7` is the high byte of the final `dac_l` word and is
  not forwarded to `enrolAddImage` or `identifyImage`.
- `WbioQueryEngineInterface` publishes this function in the
  `EngineAdapterAcceptSampleData` slot of the version-3 engine interface. The
  immediately following operation callbacks are `FUN_180020350`,
  `FUN_180020600`, and `FUN_180020b30`, with `FUN_180020b30` serving
  `EngineAdapterIdentifyFeatureSet`.

## Reference Provenance

- `usbinterface.dll` `CaptureFramedone` (`0x18001fb40`) serializes its second
  argument into this `+0xebf0` image-base slot.
- The hardware callback dispatcher supplies its retained image base from
  hardware context `+0x248`. `usbinterface.dll` `FUN_180015c60` proves that
  field is the first, TX-on member of a validated TX-on/TX-off low-DAC pair.
- Thus the production profile-9 setup frame reaching `preprocessor_init` is
  TX-on, not TX-off. The TX-off acquisition is not serialized to the engine.
- `EngineAdapterClearContext` (`FUN_18001f090`) can run between biometric
  operations without clearing initialized byte `+0x7c` or the preprocessor
  calibration workspace. A second probe therefore reuses preprocessing unless
  this sample's hardware refresh marker is one or the adapter is detached.

## Current Source Mapping

`drivers/goodix53x5/milan/runtime.c:goodix_milan_runtime_preprocess_input` and
`goodix_milan_runtime_initialize_setup` in `runtime.h` implement the copied
reference/live setup and preprocessing handoff. Enrollment has one copied live
frame per runtime input from `device/enroll.c:goodix_enroll_start_task`; the
native adapter's unused second live-frame copy is not represented there.
