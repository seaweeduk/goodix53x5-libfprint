## Recovered Layout

The packed bitmap/matrix tags map to live feature offsets as follows:

```text
tag b2 -> matrix pointer +0x08
tag cf -> matrix pointer +0x10
tag cd -> matrix pointer +0x18
tag ce -> packed bytes in the 200-byte field at +0x28 (72 for type 12)
          and derived packed-matrix pointer at +0x140
```

Tag `ce` copies at most 200 bytes, constructs a temporary descriptor with
`FUN_1800721a0`, and packs/materializes it through `FUN_180073950`. The scalar
tag run populates `+0x108..+0x150`; packed tags `b5`, `b6`, `bc`, and `be` map to
`+0x110`, `+0x114`, `+0x12c`, and `+0x134`. `b6` is the persisted relation-row
base used in matrix slot `feature[max(i,j)].b6 + min(i,j)`, while the other
three listed fields include the exact keys used by
`FUN_1800607b0`. Optional packed tag `c7` (`-0x39`) maps to `+0x150` at
`0x18003e02c`. Feature decoding does not touch template order at `+0x87e8`.

For type 12, the 32-byte record branch at `0x18003d943..0x18003db0a` initially
zeros foreground, strength, bytes `36..39`, and bytes `48..55`, then restores
only the fields present in each packed record. After all tags are decoded,
`0x18003db45..0x18003e25f` reconstructs foreground from scalar `b7/+0x118`:
indices below the signed boundary become zero and the rest become one. Thus the
packed record body is not an independent source of partition classes.

The exact type-12 record mapping is:

```text
packed  0.. 3 -> position/orientation composite
packed  4..19 -> live +0x10..+0x1f, copied directly
packed 20..23 -> live +0x20..+0x23
packed 24..31 -> live +0x28..+0x2f
```

The position decoder writes `x = (position >> 16) & 0xfff0` and
`y = (position >> 4) & 0xfff0`. Orientation bytes below `0x80` decode as
`byte << 8`; bytes at or above `0x80` decode as `(0x80 - byte) << 8`. The low
four coordinate bits and low eight orientation bits are not serialized.

Live strength `+0x08`, bytes `+0x24..+0x27`, and bytes `+0x30..+0x37` are
explicitly zeroed. Vertical class `+0x0c` is omitted from the packed record but
is reconstructed in the post-tag foreground loop. It uses unsigned decoded y:
class one below `0x1400`, class two at or above
`uint16_t((template_rows << 8) - 0x1400)`, and class zero otherwise. Profile-9
rows are 88, giving the upper threshold `0x4400`. This field is derived live
state, not a separately persisted record value.

This leaf initially installs packed descriptor bytes `4..19` directly. Complete
type-12 template decode subsequently reaches `FUN_18003fef0`, which applies
`FUN_180047ae0(record, 0)` to every live record. That helper deinterleaves the
eight descriptor byte pairs and exchanges their low nibbles with swap order
`0,1,1,0,1,0,0,1`, restoring the two live descriptor halves. It preserves live
`+0x20..+0x23`, zeros `+0x24..+0x27`, and leaves `+0x28..+0x37` unchanged in
mode zero. The initial direct copy is therefore not the descriptor state
supplied by complete unpack to matching.

Before that descriptor inverse, `FUN_18003fef0` at
`0x180040280..0x18004028c` tests the decoded orientation as a signed word and
adds `0x3244` to negative values, storing the word result. Nonnegative values
are unchanged. This is a complete-unpack normalization, not part of the leaf
position decoder. Reencoding a complete-unpack feature therefore uses the
normalized orientation rather than necessarily preserving the original
sign/magnitude byte.

### Type-12 Extraction Orientation Invariant

`FUN_18004bbb0` selects the type-12 antipodal histogram mode at
`0x18004bc63..0x18004bc9f`. In `FUN_1800496c0`, each contribution is added to
both bins separated by 18 (`0x1800498e7..0x180049913`), so the 36-bin histogram
has period 18, including dword wrapping. The circular smoothing preserves that
period. Both smoothing implementations finish with a logical dword right shift
by four (`0x180049a36`, `0x180049a90`), bounding every output by `0x0fffffff`.
The unsigned strict-maximum scan (`0x180049aa3..0x180049ac5`) keeps the first
maximum, hence an index in `0..17`, and returns that index plus 18.

For the selected bin `j` in `18..35`, let the adjacent histogram values be
`A` and `B`, with selected value `C`. Then `A,B <= C`. The materializer's
dword products `2*A`, `2*B`, and `4*C` fit without wrapping under the smoothing
bound. At `0x18004bd60..0x18004bd96`, its signed-qword divisor is
`D = 2*A + 2*B - 4*C`. For a completed materialization, `D != 0`; writing
`s = (C-A) + (C-B)` gives `D = -2*s` and `s > 0`. The correction is
`trunc_zero(((A-B)*512+s)/(-2*s))`, in `[-256,255]` because `|A-B| <= s`.
Thus the interpolated word `512*j + correction` lies in `0x2300..0x46ff`;
neither the signed-word wrap nor the one-step `0x4800` adjustment changes it.

At `0x18004bde5..0x18004be1a`, the materializer computes
`q = floor(interpolated*0x6488/(36*512))`, writes `q-0x3244`, and for type 12
adds `0x3244` back if the result is negative. Since
`0 <= interpolated < 0x4800`, `0 <= q < 0x6488`, and the stored orientation is
in `0..0x3243`. `FUN_180049b90` then rounds this nonnegative value with
`(orientation+0x80)&0xffffff00` at `0x18004a570..0x18004a5a4`, yielding
`0x0000..0x3200` in steps of `0x100`. Successful ordinary type-12 extraction
therefore cannot supply a negative orientation to feature serialization.

### Persistence Preservation

The same extraction loop rounds both coordinates with `(coordinate+8)&0xfff0`
at `0x18004a550..0x18004a56c`. Their shifted contributions to the encoder's
position composite therefore leave its low byte clear. The orientation range
above emits only bytes in `0x00..0x32`, without coordinate contamination.

Enrollment copies the selected prefix of whole 56-byte records through
`FUN_1800422e0` (`0x180042404..0x180042420`). Study append, replacement, and
queue cloning use `FUN_180037690`, called at `0x1800457f3`, `0x1800458fd`, and
`0x180045ba4`, respectively. That helper either copies all records or selects
by strength and copies whole records, then partitions them with
`FUN_180037480`; orientation at record `+0x06` is preserved. Broken-level
filtering in `FUN_18004db10` likewise removes records by moving whole 56-byte
records. Descriptor conversion and its inverse operate beyond the first
16 record bytes and do not change orientation.

Enrollment relation composition in `FUN_180042840`, `FUN_180043110`, and
`FUN_18007a040`, and study relation composition in `FUN_180045d40` and
`FUN_180046430`, write the template's 28-byte relation cells, not transformed
feature records. `FUN_1800469f0` installs copied or queued feature objects;
its subsequent `FUN_180047120` updates masks and scalar state, not record
orientations. These persistence transfers retain the extraction sign and
coordinate-alignment invariants rather than rotating the stored records.

Consequently producer-emitted type-12 records decode to nonnegative
orientations in `0x0000..0x3200`, and reencoding retains that range. Repeated
decode, enrollment/study copying, and encode cycles preserve the invariant.
The complete-unpack negative-orientation adjustment is unreachable for this
ordinary producer family. The corresponding source extraction rounding is in
`drivers/goodix53x5/milan/feature/materialization.c`; the feature-record
pack/unpack boundary is in `drivers/goodix53x5/milan/template/codec.c`.

The DLL is permissive at this boundary. If `b7 >= record_count`, it first changes
the live boundary to `record_count - 1`; a nonempty all-zero partition therefore
cannot round-trip through this decoder. The endpoint `b7 == record_count` is a
valid extractor output when every record has low class zero. Values above the
count are invalid inputs.
Negative `b7` is retained and makes all records class one; later consumers can
use that unsafe metadata. Current source intentionally fails closed when a
parsed partition is negative or greater than the count, while accepting the safe
mathematical endpoint `b7 == record_count` and reconstructing all records as zero
(`drivers/goodix53x5/milan/template/codec.c:70-116` plus consumer validation).
An absent `c7` remains zero because the source parser clears the complete view
before scanning and consumes `c7` only as an optional final five-byte field at
`drivers/goodix53x5/milan/template/codec.c:157-213`.

Tag `bf` delegates its presence/length/payload body to `FUN_1800410f0`. Valid
completed profile-9 probes decode presence one, dword length `0x1abc`, and an
exact `0x1abc`-byte owned payload at live `+0x160`. The generic leaf also accepts
an absent presence byte, but that form is not the completed identify-probe
contract.

This clamp matters when a packed singleton is used as transport into the DLL. A
one-record feature with `b7 == record_count == 1` reaches `FUN_180042c30` with
live `b7 == 0`, so that path is not equivalent to supplying the original live
extractor feature. Such endpoint inputs cannot discriminate enrollment graph or
capacity behavior; controls with `b7 < record_count` avoid the lossy round trip.
`goodix_match_combine_templates()` models successive current-extractor
singletons and deliberately preserves the valid `b7 == record_count` endpoint;
it is not an importer for arbitrary saved one-feature galleries.

The `b5` case at `0x18003ded1..0x18003dedd` copies the packed dword directly to
live `+0x110`; it does not require zero or one. This makes non-Boolean `b5`
structurally decodable DLL input. It is relevant to flag-zero replacement:
`FUN_180045530` admits any nonzero `b5` to its ranking scan but counts only exact
one in its three-zero-residual validation. Production `c182b140` keeps native
decoding permissive and preserves that nonzero-scan/exact-one-count policy split;
the controlled generic-input boundary is documented in `FUN_180045530.md`.

Packed tag `bb` maps to `+0x128`, but it is not authoritative for production
type 12 after complete unpack: `FUN_18003e3a0` reaches `FUN_180047550`, which
recomputes `bb` from masks, active state, dimensions, live reference, and the
relation matrix. A missing optional `c7` remains zero and is not involved in
that normalization.

The packed mask, partition boundary, and extraction classification remain
independent fields; none is reconstructed from either of the others.

Evidence is the switch over signed tag bytes in `0x18003d6c0..0x18003e315`:
cases `-0x4e`, `-0x31`, `-0x33`, and `-0x32` are `b2`, `cf`, `cd`, and `ce`.
