## Recovered Behavior

For profile 9/type 12, the complete feature-element order is:

```text
95(length)
  b2(311: c1=52,c2=44,c3=UINT32_MAX,c4=8,c5=286,payload[286])
  cf(311: same nested dimensions and payload length)
  ce(72, payload[72])
  cd(311: same nested dimensions and payload length)
  b3(record_count)
  bf(1, 0x1abc, payload[0x1abc])
  b4(record_count * 32, records[])
  b5 b6 b7 b8 b9 ba bb bc bd be c0
  [c7 when live +0x150 != 0]
```

Each outer bitmap block is 316 bytes including its tag and length. The three
bitmap payloads are packed `52x44` one-bit planes (`2288 / 8 == 286` bytes).
The `ce` payload is the packed quarter-resolution `26x22` mask, rounded once to
72 bytes. The anti-fake block is 6 framing bytes plus an exact `0x1abc`-byte
copy. Consequently the complete type-12 feature size is exactly
`7945 + 32 * record_count + (c7 != 0 ? 5 : 0)` bytes, including the leading
`95` element header.

After maps, anti-fake data, and records, the helper maps live feature dwords to
tags `b5..be` consecutively from offsets `+0x110..+0x134`; tag `c0` comes from
`+0x14c`, and optional `c7` comes from `+0x150`. Consequently the
`FUN_1800607b0` sort keys are serialized exactly as `b5` (`+0x110`), `be`
(`+0x134`), and `bc` (`+0x12c`).

The complete `b5..be` run, including `bb` at `+0x128`, is always emitted as
five-byte tag/dword elements even when a value is zero. `c7` is different: it is
emitted only when `+0x150 != 0`, adding exactly five bytes to the feature
element. Setting `bb` to zero therefore cannot explain a five-byte size delta;
adding or removing `c7` can.

The helper writes feature bytes only. It does not read or write the template
order vector.

For profile-9/type-12, tag `ce` is mandatory and comes directly from live feature
`+0x28`. At `0x180040bb3..0x180040bee`, the helper computes
`ceil(width/4) * ceil(height/4)` bits, rounds that count up to bytes, and copies
the exact prefix. Fixed `104x88` geometry therefore emits a length dword of 72
and the exact 72 bytes generated by `FUN_180072b60`; no dense mask or record
field is consulted during this copy.

Type 12 selects the 32-byte record branch at `0x180040c82..0x180040d93`. The
record body begins with
`position = (uint32_t(x) << 16) | (uint32_t(y) << 4) | packed_orientation`.
Nonnegative orientation emits `orientation >> 8`; negative orientation emits
`((-orientation) >> 8) + 0x80`, truncated to one byte. `FUN_18004c9f0` then
converts the two live eight-byte descriptor halves to 16 packed bytes with the
fixed order `[0,1,1,0,1,0,0,1]`. Packed bytes `20..23` copy live
`+0x20..+0x23`, and packed bytes `24..31` copy live `+0x28..+0x2f`.
Foreground `+0x00`, strength `+0x08`, vertical class `+0x0c`, live
`+0x24..+0x27`, and live `+0x30..+0x37` are omitted. The mandatory `b7` scalar at
`0x180041021..0x18004102b` is the sole packed owner of the foreground partition
boundary. The optional `c7` write remains independent at
`0x180041096..0x1800410ba`.

Type-12 serialization omits live record spans `+0x24..+0x27` and
`+0x30..+0x37`. Transform-mode effects confined to those spans therefore do not
affect packed `b4` records.

The anti-fake subencoder `FUN_180040840` emits a two-byte absent form when live
feature `+0x160` is null, while paired size helper `FUN_180040980` includes the
fixed populated anti-fake cost. Calling this pair before `FUN_1800392f0`
therefore cannot produce a size-consistent profile-9 probe element. After
`identifyImage` returns, `+0x160` is populated and the size/encode pair can be
used before `templateStudy` destroys the retained probe.

`FUN_180040840` copies the complete `0x1abc` anti-fake object without
normalizing its contents. Bytes influenced by the undefined one-past source in
`FUN_1800392f0` therefore remain present in the serialized `bf` payload. The
pair score at anti-fake `+0x1ab4` is part of the same exact copy.
