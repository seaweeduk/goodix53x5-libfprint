# FUN_1800392f0

Current profile-9/type-12 runtime assigns semantic zero to this function's one
proven one-past feature-mask source. `canonical-zero-v1` changes only source
index 2,288; it does not weaken parity for any defined input or anti-fake output.

## Audit Scope

Profile-9 anti-fake builder containing the call at `0x180039798` to the
anti-fake feature-record stage. This note was created before first Ghidra
inspection for the one-byte feature-mask boundary-read audit.

## Questions

- Which instruction reads one byte beyond the nominal `52x44` feature matrix?
- What address is read on the final sensor row, and how many loop iterations
  consume that address?
- Which defined production object or field supplies that byte before the
  anti-fake builder runs?
- Can native code derive the same value from defined source state without
  reproducing an out-of-bounds access or accepting a fixture-provided gate?

## Audit Findings

- The production anti-fake builder receives the full `0x3048c` preprocessor
  workspace, but directly consumes only the setup/calibration map at `+0x9924`,
  the selected-output scalar at `+0x26484`, and the processed 8-bit image at
  `+0x1cb64` along this path. It separately receives the live raw frame and the
  metadata-derived residual offset.
- The `52x44` feature matrix below comes from the live feature object at
  feature-object `+0x20`; TX-off and FDT data are not direct inputs to this
  builder.
- The feature matrix at feature-object `+0x20` is a `52x44` one-byte matrix.
  Its descriptor stores width `52` at `+0x00`, byte count `2288` at `+0x0c`,
  and data at `+0x18`.
- `FUN_180068700` (`MatCreatNew`) allocates exactly `0x20 + 2288` bytes for
  that descriptor and payload. There is no defined payload byte at index 2288.
- The load at `0x18003944c` is
  `matrix->data[(y / 2) * matrix->width + (x / 2)]`. The loops cover sensor
  rows `0..87` and columns `2..105`.
- At `y=86/87` and `x=104/105`, the expression is index `2288`. Windows thus
  reads the same one-past byte four times while producing the lower-right `2x2`
  output. The byte is heap residue and changes when breakpoint instrumentation
  changes the allocator layout.
- The instruction normalizes any nonzero byte to `1`, but the source remains
  allocator residue rather than a defined production field. Independent
  corrected TX-on hardware-metadata runs observed both active and inactive
  bytes; breakpoint instrumentation can likewise change the result.
- Native code preserves the observed Windows indexing for all in-range reads,
  but substitutes normalized byte `0` only when Windows would read index
  `2288`. No fixture-provided active/inactive sequence remains.
- Candidate records/count are constructed by `FUN_18003b0b0` from the
  morphology mask before `FUN_18004b770` enriches each retained record. The
  latter does not own count or candidate admission.

## Type-12 Packed-Mask Bound

The function clears the fixed 2,000-byte mask at anti-fake offset `+0x12dc`
with `memset(..., 0, 0x7d0)` at `0x18003961b..0x180039632`. For nonzero chip
type, including type 12, `0x180039740..0x180039787` then packs every bit of the
full `rows * columns` dense mask. The loop has no independent comparison
against the 16,000-bit destination capacity; it relies on the engine's decoded
profile geometry. Profile 9 is safe because its fixed `88x108` geometry is
9,504 bits (1,188 bytes).

The native Linux builder exposes rows and columns as generic API arguments, so
it cannot inherit that fixed-profile precondition from the DLL caller. Its
type-12 final repack must reject `rows * columns > 2000 * 8` after checked
multiplication. Without that guard, synthetic-valid dimensions can pass the
earlier cropped-width mask check and overwrite anti-fake scalar fields and then
the containing allocation; `1000x20` is a controlled example because
`1000 * (20 - 4)` is exactly 16,000 bits while the final full-width mask is
20,000 bits.

Production commit `3658c48f6d2027c60e458f05ab703d836c8a4ddd` adds the
checked multiplication and capacity guard before the type-12 repack. Focused
AddressSanitizer and UndefinedBehaviorSanitizer validation established that the
oversized `1000x20` control now returns `-1` without a sanitizer report or
corruption at the former scalar-overwrite boundary. The normal `88x108`
type-12 control still returns success, and its complete 6,844-byte anti-fake
blob is byte-identical before and after the guard. The existing Milan synthetic,
state, and runtime suites all pass in 3.394 seconds.

## Profile-9/Type-12 Construction Contract

The two production callers are `enrolAddImage:0x18000171b` and
`identifyImage:0x180001dd3`. Both pack profile geometry and chip information in
the third argument: rows are bits `14..22`, columns are bits `23..31`, and chip
type is bits `3..8`. The active profile decodes to rows `88`, columns `108`, and
chip type `12`. The live feature object supplies a `52x44` one-byte matrix at
feature `+0x20`; the calibration workspace supplies the `88x108` setup map at
`+0x9924`, primary classification plane at `+0x1cb64`, and calibration scalar at
`+0x26484`.

`enrolAddImage` and `identifyImage` independently derive the fifth builder
argument with wrapping 32-bit multiplication followed by signed division
toward zero:

```c
uint32_t difference = (uint32_t)dac_high - dac_low;
uint32_t product = difference * t_code * 0x11b;
if (chip_type == 0x11)
  product = (difference + 0x55) * t_code * 0x146;
int32_t sensor_offset = (int32_t)product / 1000;
```

Only chip type `0x11` selects the alternate addend and scale. Type 12 selects
the `0x11b` path. The production metadata tuple `t_code=0x79`,
`dac_high=0x7d`, `dac_low=0xc6` yields `-2499`.

The builder allocates or reuses feature `+0x160`, then clears exactly `0x1abc`
bytes at `0x180039369..0x18003937b`. Its fixed working domains are:

| Material | Profile-9/type-12 extent |
|---|---:|
| anti-fake object | 6,844 bytes (`0x1abc`) |
| feature source | `52x44`, 2,288 defined bytes |
| dense morphology mask | `88x108`, 9,504 bytes |
| morphology temporary | `88x108`, 9,504 bytes |
| residual | `88x108` `uint16_t`, 19,008 bytes |
| classification copy scratch | `88x108`, 9,504 bytes |
| statistics high-pass scratch | `88x108` `uint16_t`, 19,008 bytes |
| boundary class and thinning scratch | two `88x108` byte planes, 9,504 bytes each |
| block-variation maxima/validity | 48 `uint16_t` maxima plus 48 validity bytes |
| model vector | 51 signed dwords, 204 bytes |
| packed-mask field | 2,000 bytes |
| descriptor-update domain | `104x88`, 9,152 sequential residual values |
| descriptor dense orientation | `104x88`, 9,152 bytes |
| descriptor magnitude | `104x88` dwords, 36,608 bytes |
| descriptor gradient orientation | `104x88` signed words, 18,304 bytes |

The classification copy scratch is populated on the nonzero-chip branch but is
not consumed afterward. Boundary classification instead consumes workspace
`+0x1cb64` directly. The descriptor update deliberately takes the first 9,152
contiguous residual values under the live feature's `104x88` geometry; it does
not crop two columns from each `108`-wide row.

### Mask Serialization

For type 12, the final mask is the complete morphology plane in row-major
`88x108` order. Dense pixel `i` maps to byte `i >> 3`, bit `i & 7`; bits are
least-significant first. Exactly 9,504 bits, or 1,188 bytes, are addressable and
the remaining 812 bytes retain the preceding zero clear. This replaces the
cropped serialization used by chip type zero. Candidate construction receives
the dense plane before serialization and type 12 does not apply the chip-zero
coordinate subtraction.

### Native Failure Surface

The function returns `void`, performs no pointer, dimension, product, capacity,
or allocation checks, and dereferences allocation results immediately. Its
fixed production inputs satisfy the implicit dimensions and the 16,000-bit mask
capacity. Malformed geometry, missing objects, allocation failure, or an
oversized packed plane can fault or corrupt memory; there is no recoverable
failure object. If execution faults, already-published fields remain partial in
the order above.

## Current Source Mapping

`goodix_milan_antifake_build()` and `milan_antifake_build_class()` preserve the
successful profile-9/type-12 outputs with these structural differences:

- residual construction precedes mask construction, but the two stages have no
  data dependency;
- the source mask helper temporarily serializes cropped columns `2..105` as
  `88x104` LSB-first bits so candidate collection can recover the same dense
  admission bits; type 12 clears and replaces that field with the native
  full-width `88x108` serialization before return;
- aggregate scalar values are computed into locals and published together,
  whereas the DLL publishes each direct output as its producer returns;
- descriptor update is called with rows `88`, columns `104`, which preserves
  the DLL's sequential 9,152-value interpretation rather than row-cropping;
- checked API preconditions and allocation failures return `-1`. Depending on
  the failure point, the source can leave the caller's old object untouched or
  a cleared/partially populated object; the DLL has no corresponding status;
- the type-12 capacity check rejects a full-width mask above 16,000 bits. It is
  inactive for the production 9,504-bit geometry.

On a successful call, field offsets, final publication values, candidate
handoff, full-width mask replacement, feature-update dimensions, and final
pair-score publication are the same.

`goodix_milan_antifake_build_with_boundary()` has no DLL runtime counterpart.
For exactly type 12, `88x108`, and a 2,288-byte feature source, it first builds
the canonical-zero object, then builds a second object from the same defined
bytes plus a supplied nonzero byte at source index 2,288. It compares all 6,844
bytes, including reserved zeros and the complete packed-mask tail. Equality is
`STABLE`; any byte difference is `AMBIGUOUS` and returns the diagnostic status
`1`. The result, when requested, retains both complete projections and both
candidate counts. Primary-build failure, alternate allocation failure, or
alternate-build failure returns `-1`; non-target geometry returns the primary
status with classification `NOT_EVALUATED`. The normal production constructor
does not call this alternate path.

## Independent Static Recheck

A fresh Ghidra audit on 2026-07-25 independently confirmed the complete source
ownership chain rather than relying on the prior boundary note. The active
profile-9 producer `FUN_18006eff0` halves the `104x88` matrix, requests an exact
`52x44x1` allocation through `FUN_180068700`, and writes only indices
`0..2287`. `FUN_180068700` requests exactly `0x20 + payload_size` from the
`malloc` thunk and sets data to allocation `+0x20`; no constructor, producer,
clone, or caller initializes index 2,288 as a sentinel or halo.

The builder then iterates destination columns `2..105` while indexing this
crop-relative 52-column source as `x / 2`. That maps the first destination pair
to source column 1, rolls the final pair into the following row's column 0, and
on the final row reaches index 2,288. A crop-relative expression such as
`(x - 2) / 2` would instead cover source columns `0..51`. This establishes an
off-by-one coordinate mismatch and undefined source byte in the shipped binary;
vendor source-level intent remains unknowable, but no static evidence supports
an intentional defined boundary input.

## Controlled-Boundary Oracle Contract

The production-path intervention point is outside this function at
`identifyImage:0x180001dbd`. The normal extractor has already produced the live
feature, but this function has not begun. The oracle replaces only the owned
`+0x20` matrix allocation with a DLL-allocator-owned 2,289-byte shadow. Its
32-byte header, 2,288 in-range bytes, stored size `2288`, dimensions `52x44`,
stride `52`, and element size `1` remain unchanged; only physical byte 2,288 is
added and set explicitly. This function then executes unchanged, including the
four loads at `0x18003944c` and all downstream anti-fake construction.

Paired sentinel `0/1` runs must establish the complete output footprint before
the zero case can become reference authority. Wrong-byte and broader-zeroing
controls are invalid interventions because they change defined matrix bytes.

## Production Lifecycle Derivability Verdict

The byte is not derivable from the production target lifecycle. The complete
owner chain is `FUN_18004ae70 -> FUN_18006eff0 -> FUN_180068700 ->
FUN_180003800`: one exact 2,320-byte allocation contains the 32-byte matrix
header and 2,288-byte payload. The producer writes every payload byte exactly
once and no caller, clone, initializer, profile setup, service setup, or
destructor allocates or initializes payload index 2,288. The read is the first
byte outside that allocation, not the untouched tail of feature scratch matrix
`+0x158` documented in `FUN_180048260`.

Allocation adjacency is a property of the process CRT heap at that instant.
The out-of-object address can contain allocator metadata or another allocation's
contents; matrix ownership exposes neither. Reuse does not make it source state:
the allocator import is `malloc`, not a zeroing allocator, and no Windows
profile-9/subtype-12/WBF field constrains the next byte. Corrected minimal runs
and breakpoint-instrumented runs observed both zero and nonzero while all 2,288
defined bytes remained fixed. Because `0x18003944c` normalizes the load, the
complete reachable semantic domain is exactly two classes: zero and nonzero.

Native live construction uses the previously established deterministic
replacement: semantic zero at this one source before candidate construction,
descriptor enrichment, anti-fake statistics/model scalars, packed morphology,
and feature update. The paired full-`0x1abc` zero/nonzero constructor remains an
offline diagnostic. It confirms that canonical-zero templates may differ from
Windows allocator-residue bytes, but those differences are not a new parity
defect and do not authorize a live retry policy. Defined-byte parity and score,
decision, index, action, update, relation, study, and persistence behavior remain
mandatory under canonical zero.
