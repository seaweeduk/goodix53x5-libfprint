- The load at `0x18003944c` is
  `matrix->data[(y / 2) * matrix->width + (x / 2)]`. The loops cover sensor

## Type-12 Packed-Mask Bound

The function clears the fixed 2,000-byte mask at anti-fake offset `+0x12dc`
with `memset(..., 0, 0x7d0)` at `0x18003961b..0x180039632`. For nonzero chip
type, including type 12, `0x180039740..0x180039787` then packs every bit of the
full `rows * columns` dense mask. The loop has no independent comparison
against the 16,000-bit destination capacity; it relies on the engine's decoded
profile geometry. Profile 9 is safe because its fixed `88x108` geometry is
9,504 bits (1,188 bytes).

The native Linux builder exposes rows and columns as generic API arguments, so
it cannot inherit that fixed-profile precondition from the DLL caller. Its
type-12 final repack must reject `rows * columns > 2000 * 8` after checked
multiplication. Without that guard, synthetic-valid dimensions can pass the
earlier cropped-width mask check and overwrite anti-fake scalar fields and then
the containing allocation; `1000x20` is a controlled example because
`1000 * (20 - 4)` is exactly 16,000 bits while the final full-width mask is
20,000 bits.

Production commit `3658c48f6d2027c60e458f05ab703d836c8a4ddd` adds the
checked multiplication and capacity guard before the type-12 repack. Focused
AddressSanitizer and UndefinedBehaviorSanitizer validation established that the
oversized `1000x20` control now returns `-1` without a sanitizer report or
corruption at the former scalar-overwrite boundary. The normal `88x108`
type-12 control still returns success, and its complete 6,844-byte anti-fake
blob is byte-identical before and after the guard. The existing Milan synthetic,
state, and runtime suites all pass in 3.394 seconds.

## Independent Static Recheck

A fresh Ghidra audit on 2026-07-25 independently confirmed the complete source
ownership chain rather than relying on the prior boundary note. The active
profile-9 producer `FUN_18006eff0` halves the `104x88` matrix, requests an exact
`52x44x1` allocation through `FUN_180068700`, and writes only indices
`0..2287`. `FUN_180068700` requests exactly `0x20 + payload_size` from the
`malloc` thunk and sets data to allocation `+0x20`; no constructor, producer,
clone, or caller initializes index 2,288 as a sentinel or halo.

The builder then iterates destination columns `2..105` while indexing this
crop-relative 52-column source as `x / 2`. That maps the first destination pair
to source column 1, rolls the final pair into the following row's column 0, and
on the final row reaches index 2,288. A crop-relative expression such as
`(x - 2) / 2` would instead cover source columns `0..51`. This establishes an
off-by-one coordinate mismatch and undefined source byte in the shipped binary;
vendor source-level intent remains unknowable, but no static evidence supports
an intentional defined boundary input.

## Production Lifecycle Derivability Verdict

The byte is not derivable from the production target lifecycle. The complete
owner chain is `FUN_18004ae70 -> FUN_18006eff0 -> FUN_180068700 ->
FUN_180003800`: one exact 2,320-byte allocation contains the 32-byte matrix
header and 2,288-byte payload. The producer writes every payload byte exactly
once and no caller, clone, initializer, profile setup, service setup, or
destructor allocates or initializes payload index 2,288. The read is the first
byte outside that allocation, not the untouched tail of feature scratch matrix
`+0x158` documented in `FUN_180048260`.

Allocation adjacency is a property of the process CRT heap at that instant.
The out-of-object address can contain allocator metadata or another allocation's
contents; matrix ownership exposes neither. Reuse does not make it source state:
the allocator import is `malloc`, not a zeroing allocator, and no Windows
profile-9/subtype-12/WBF field constrains the next byte. Corrected minimal runs
and breakpoint-instrumented runs observed both zero and nonzero while all 2,288
defined bytes remained fixed. Because `0x18003944c` normalizes the load, the
complete reachable semantic domain is exactly two classes: zero and nonzero.

Native live construction uses the previously established deterministic
replacement: semantic zero at this one source before candidate construction,
descriptor enrichment, anti-fake statistics/model scalars, packed morphology,
and feature update. The paired full-`0x1abc` zero/nonzero constructor remains an
offline diagnostic. It confirms that canonical-zero templates may differ from
Windows allocator-residue bytes, but those differences are not a new parity
defect and do not authorize a live retry policy. Defined-byte parity and score,
decision, index, action, update, relation, study, and persistence behavior remain
mandatory under canonical zero.
