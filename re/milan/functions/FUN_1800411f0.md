## Contract

The five-argument Windows x64 ABI is:

```c
void propagate_lower(context, pivot_to_reference, int32_t pivot,
                     overlap_context, int32_t threshold);
```

Profile 9 supplies threshold 205. The helper itself uses the supplied signed
threshold and returns immediately when `pivot <= 0`. It does not validate the
context, reference, feature pointers, row bases, or feature count.

The candidate scan is signed and descending: `pivot-1, pivot-2, ..., 0`. An
exact active word of `1` is skipped; any other value, including another nonzero
value, remains eligible. For each eligible candidate, the helper searches its
worklist in reverse append order. A candidate/node relation is eligible only
when its leading signed dword is nonnegative. Undefined negative slots are
skipped without calling overlap. `FUN_180071d40` receives the worklist-node
feature first, candidate feature second, the canonical higher/lower slot
transform, and the supplied overlap context. Admission is exactly:

```text
signed_overlap_return > signed_threshold
```

Equality at 205 is rejected and 206 is admitted. The first passing node in the
reverse search wins; no score maximization or tie replacement occurs.

The worklist starts as `[pivot]`. Accepted candidates are appended in outer
scan order, which is descending physical index. Its stack storage is 52 signed
dwords at `[rbp-0x70, rbp+0x60)`, with no explicit capacity check. Natural
profile-9 enrollment has at most 40 live features; at that boundary the caller's
current feature is 39, a bridge pivot is at most 38, and this helper needs at
most 39 entries. Direct out-of-profile controls with all 50 allocated features
also fit: pivot 48 admits candidates through zero and uses 49 entries in both
DLL and source. Counts above the 50-feature allocation contract are unbounded
for this helper and unsafe.

For a candidate admitted from worklist position `p`, let `E(a,b)` be the six
stored words in the canonical triangular slot for `a,b`. Native computes:

```text
path = E(worklist[p], candidate)
for r = p-1 down to 0:
    if E(worklist[r], worklist[r+1]) is defined:
        path = compose(E(worklist[r], worklist[r+1]), path)
candidate_to_pivot = invert(path)
candidate_to_reference = compose(pivot_to_reference, candidate_to_pivot)
```

Every `compose` is `FUN_180068860`, so it normalizes its linear result before
the next hop. A two- or three-hop route is therefore not one raw matrix product
with final-only normalization. Missing adjacent fold slots are silently skipped.
The worklist records no parent links: when an admitted node was reached through
an older worklist position, a later route through that node still folds the
adjacent worklist prefix, not a separately retained historical parent chain.

`pivot_to_reference` is the caller's stack-local transform passed in `RDX` and
saved at entry. The helper never reloads the pivot/reference canonical slot.
This avoids an additional storage inversion and fixed-point round trip.

After composition, native writes the candidate active word to `1` first. It
stores `candidate_to_reference` directly when `candidate >= live_reference` and
stores its inverse when `candidate < live_reference`; this keeps every
triangular relation oriented from the higher physical index to the lower. The
six transform words are written before the slot's leading dword is set to zero.
Singular inversion copies its input and is not a failure. Composition and
inversion have no status return, and native has no recoverable store failure.

Each physical candidate is visited once and appended at most once, so ordinary
cycles or duplicate edges cannot re-enqueue it. Multiple available routes are
resolved solely by newest-to-oldest worklist search. A failed overlap on a later
candidate does not roll back already written relations or active words; search
continues with older defined nodes and then with the next candidate.

## Current Source Mapping

`drivers/goodix53x5/milan/enrollment/propagation.c:23-29` initializes the
worklist, `:30-47` implements the descending/reverse admission search,
`:48-58` folds the worklist prefix, and `:59-69` inverts, composes, stores,

`drivers/goodix53x5/milan/enrollment/template.c:93-105`; bridge-local creation,

the stored transform; its callback argument order is source-local and need not
match the DLL helper's literal feature-argument order.

Valid profile-9 behavior is exact. The remaining differences are:

- Native skips only active word `1`; source `propagation.c:32` skips every
  nonzero value. Natural active words are Boolean, so this is unreachable in
  valid enrollment. A direct `active=2` control is distinguishing: DLL admits
  and canonicalizes the candidate, while source leaves value 2 untouched.
- Source validates top-level arguments and can return `-1`; native is `void` and
  assumes caller invariants. Source stores before activation, while native
  activates before its infallible raw store. With a malformed unmarked reference,
  source preserves earlier writes, rejects the later self-reference store, and
  leaves that feature inactive; DLL marks it active and publishes into the raw
  row-base-derived slot. The maintained bridge always marks a valid reference
  active, so this is defensive-state divergence, not natural profile-9 reachability.
- Source's worklist has 50 entries and relies on matrix construction for that
  bound. Both propagation helpers can process the generic allocation safely,
  but the profile-9 admission limit is 40 and is owned by the top-level combiner
  contract documented in `FUN_180042c30.md`.
- If lower source propagation returns `-1`, `template.c:149-153` short-circuits
  and does not run higher propagation. Native always calls both void helpers.
  No compose, invert, overlap, or store status can trigger this under valid DLL
  or current profile state; only malformed source state reaches it.
