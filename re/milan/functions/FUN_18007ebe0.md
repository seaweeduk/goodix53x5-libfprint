## Recovered Behavior

The function derives dense orientation support from an 8-bit image. It builds
horizontal/vertical gradient products, integral workspaces, and a radius-
controlled orientation byte per output pixel. `FUN_18004b770` supplies radius
7 and samples this output only after `FUN_18003b0b0` has fixed candidate
coordinates/count.

`FUN_18007eb30` is the other type-12-reachable caller and supplies radius `6`
for normal extraction. For each interior pixel, the signed 32-bit gradients are

```text
h = 2*(right-left) - upper_left - lower_left + upper_right + lower_right
v = 2*(lower-upper) - upper_left - upper_right + lower_left + lower_right
```

The function forms signed 32-bit `2*h*v` and `h*h-v*v`, then unsigned 32-bit
integral planes. Integral construction and rectangle subtraction deliberately
wrap modulo `2^32`; rectangle bounds clamp to indices `1..width-1` and
`1..height-1`. At every output pixel it calls `FUN_180074290` with the
second-product sum first and cross-product sum second. This transposed call is
why current `feature_atan2(y, x)` has apparently exchanged axis cases; source
owners are `feature_atan2`, `feature_integral_sum`, and
`goodix_milan_feature_enhance` in `milan/feature/enhancement.c`.

The first/last rows and columns of the gradient-product planes remain zero.
Integral construction starts at row 1, column 1; its row 0 and column 0 remain
zero. For radius 6 the inclusive rectangle is
`[max(1,x-6), min(width-1,x+6)]` by
`[max(1,y-6), min(height-1,y+6)]`, including for output border pixels.
The full width-by-height orientation plane is written, not just its interior.

For cross-product sum `y` and second-product sum `x`, the angle-only contract
of `FUN_180074290(&x, &y)` is:

- If `x == 0`, return `y > 0 ? 0 : 0x3244`; thus `(0,0)` selects `0x3244`.
- Otherwise, if `y == 0`, return `x > 0 ? 0x1922 : -0x1922`.
- Starting at `X=abs(x)`, `Y=abs(y)`, and a 16-bit angle accumulator of zero,
  perform up to 13 arithmetic-shift rotations. For iteration `i`, take both
  shifts from the old components. If `X > 0`, set
  `X -= Y_old >> i`, `Y += X_old >> i` and add table angle `i`; otherwise use
  the inverse updates and subtract the table angle. Stop when updated `X` is
  zero. Table `0x1800e13d0` is
  `[3217,1899,1003,509,256,128,64,32,16,8,4,2,1]`.
- If original `y <= 0`, return `x > 0 ? 0x3244-angle : angle-0x3244`;
  otherwise return `x < 0 ? -angle : angle`. Interpret the low 16 bits as signed.

The angle helper also overwrites its second pointed-to argument with a
gain-corrected magnitude. Dense orientation does not consume that value:
both rectangle-sum locals are assigned afresh before every call at
`0x18007f1d9`.

That reachable domain cannot exercise the helper's extreme dword wrap cases.
Each byte-derived gradient is in `[-1020,1020]`, so one cross product `2*h*v`
is at most `2080800` in magnitude and one second product `h*h-v*v` at most
`1040400`. A radius-7 rectangle contains at most 225 terms, bounding its two
signed sums by `468180000` and `234090000`; radius 6 is smaller. The full
13-step CORDIC gain therefore keeps every component below `862000000`. The
unsigned integral planes still implement native modulo-`2^32` construction,
but their rectangle results equal these in-range signed sums for every byte
image. Arbitrary independent `int32_t` arguments are not values producible by a
type-12 dense-orientation frame.

Negative angles gain period `0x6488`; degrees are
`(angle * 0x1ca6) >> 20`. The output byte is
`-76 - (degrees <= 135 ? degrees + 45 : degrees - 135)`, narrowed modulo 256.
The `<= 135` tie is exact. Six temporary dword planes are allocated over the
function's lifetime, with at most four live at once: two zero-initialized
gradient planes and two product planes first; the gradients are freed at
`0x18007ef80` and `0x18007ef88` before the two integral allocations. Products
and integrals are freed at `0x18007f26a..0x18007f288`. The DLL allocator contract
does not expose a recoverable allocation-failure result, while current source
returns `-1` and frees partial allocation state.

For the zero-product image the angle conversion produces orientation byte 45.
The radius-6 orientation is consumed only by the seven-tap image producer
`FUN_18007f2c0`; it does not own candidate count.
