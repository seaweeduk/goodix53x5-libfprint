## Recovered Behavior

The live order vector is 50 `int32_t` entries at template `+0x87e8`. This
helper selection-sorts only entries `[0, feature_count)`, where feature count is
read from template `+0x1c`. Each entry is a feature index. The descending key is:

1. feature `+0x110`, serialized tag `b5` (active state);
2. feature `+0x134`, serialized tag `be` (study generation); and
3. feature `+0x12c`, serialized tag `bc` (lifecycle ordinal).

Assembly comparisons are at `0x180060830`, `0x18006083d`, and `0x180060844`.
Swaps are at `0x180060868..0x180060875`. Counts zero and one return without a
write. Slots `[feature_count, 50)` are not inspected or changed.

The count and loop bounds use unsigned dword comparisons. All three feature
keys use signed dword comparisons (`JG` at `0x180060833/0x180060840`, `JLE`
at `0x18006084a`). Thus a `be` increment crossing `0x7fffffff` changes its
relative signed rank; the sorter neither saturates nor normalizes that field.

For match-time finalization, `FUN_180055a40` calls this helper after its
physical contributor increment loop and before publishing the aggregate Q8
score. The branch requires incoming score zero and successful compact winner
validation. Direct-positive, rescue-positive, and fallback-positive exits do
not independently call this sorter. This call changes no feature scalar,
relation, queue entry, or order-generation counter; the study dispatcher's
separate finalization owns the order-generation increment.

Sorting changes traversal indices, not the physical feature-owner array.
`FUN_18003eaf0` still emits features in physical-index order, while
`FUN_18003f290` copies the complete 200-byte order vector into tail tag `a1`.
Neither packer repeats this sort. Match-time reordered indices therefore remain
part of a packed after-match snapshot even if no study action follows.

Enrollment does not supply a descending-order precondition. `FUN_180042c30`
rewrites identity traversal after each stage, assigns `bc=i` to a new physical
slot `i`, and initializes its `be` to zero. Its capacity finalizers run at 40,
not at the ordinary 12-stage enrollment completion; see `FUN_180042c30.md`.
For an identity-ordered group of at least three equally active features with
these initial counters, incrementing any subset once cannot make the group
descending: `be` has at most two values, so some pair still has equal `be` and
ascending `bc`. Thus the match-time caller cannot infer an already-sorted
post-increment vector from those enrollment-produced keys alone.

All three comparisons replace the selected candidate only on strict greater-
than. Equal keys retain the first maximum encountered during that pass, but the
in-place selection swaps are globally unstable. For example, key classes
`[low,high,low,high]` produce `[1,3,2,0]`; a stable descending sort would
produce `[1,3,0,2]`.

tail `+0x8cf4`. The caller executes `INC dword ptr [RBX+0x8cf4]` immediately
after this helper returns at `0x1800451c6`. Thus order precedes tail, both occur
once after queue/action handling, and the 32-bit tail wraps modulo `2^32` without
carry.
