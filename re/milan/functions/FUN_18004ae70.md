## Recovered Behavior

The function allocates and populates a `0x168`-byte owned feature object from a processed image and profile configuration. It builds the high, enhanced, low, validity, and packed masks, invokes `FUN_180049b90` for candidate and descriptor materialization, applies later descriptor transformations, and calls `FUN_180037480` to partition active records. The resulting object stores its active record count at `+0xf0`, a pointer to `0x38`-byte records at `+0xf8`, and owned matrices at `+0x08`, `+0x10`, `+0x18`, `+0x20`, and `+0x140`.

For profile 9/type 12, optional packed field `c7` has two producers. The call to
`FUN_18006fb10` occurs at function entry, directly on the incoming
processed-image descriptor, before cropping, map construction, record
materialization, or any other image helper. Its decoded dword is retained in a
local. Later, when the auxiliary extraction context is present, the call to
`FUN_180048260` receives that local by pointer and may overwrite it from
extraction classification state. The final value is written to live feature
`+0x150` near function exit.

At the exported identify call, stack argument 6 is the first candidate's
internal template/configuration and stack argument 8 is the same preprocessor
auxiliary workspace passed to `identifyImage`. The authoritative profile-9
configuration words are `[12,104,88,1,1,150,150]`. Immediately before
`FUN_180048260`, this function combines those words with raw processed geometry,
the three zero-extended auxiliary bytes, entry-decoded low/high classes, and
coverage into the exact configuration documented in `FUN_180048260.md`.

The extraction classifier runs before `FUN_180049b90` record materialization
and before the final feature store. Its process-global history mutations are not
rolled back by later extraction or matching failure.

The processed-image broken-pixel mask is distinct from both feature-owned mask
representations. `FUN_18006fb10` decodes it before the centered width reduction.
The active profile-9 map builder `FUN_18006fef0` has already sampled the initial
validity into the owned `52x44` byte matrix at feature `+0x20` by
`0x18004b341`. On decoded-mask return one, `0x18004b590..0x18004b5fa` selects
radius two for decoded high class below four, or radius five plus clearing for
high class four/five, and calls `FUN_18004db10`. Mode one clears the caller's
separate `104x88` validity matrix; it does not revisit feature `+0x20`. This is
after `FUN_180049b90` has produced quantized records and before
`FUN_180072b60`, per-record `FUN_180047ae0` transformation, and
`FUN_180037480` partitioning. The `108x88` decoded mask is freed immediately at
`0x18004b603`.

The caller predicate at `0x18004b58b..0x18004b590` tests only decoded-mask
availability; it does not test live count `+0xf0`. It passes the allocated
record pointer and `&feature->count` even when that count is zero.
`FUN_18004db10:0x18004db49..0x18004db4e` then returns before neighborhood
construction or mode-one clearing unless the signed count is positive. A
zero-record feature therefore retains its pre-filter `104x88` validity matrix,
and the following unconditional inline/rescue construction publishes masks
derived from that unchanged matrix.

Type 12 reaches the centered `104x88` extraction geometry through
`FUN_180070690` at `0x18004b08d`, but the broken-mask filter receives original
width 108 at `0x18004b5f6` and uses record coordinates without adding the
two-column centering offset. Its separate feature-mask width is 104 from
`0x18004b5ea..0x18004b5f0`.

The inline-mask handoff is also explicit. `FUN_180072b60` at `0x18004b613`
reduces the finalized, potentially cleared `104x88` validity matrix to the
72-byte row-contiguous `26x22` mask at live feature `+0x28`.
`FUN_1800721a0` at `0x18004b629` immediately expands that mask in mode 1 to a
temporary `52x44` byte plane; `FUN_180073950` packs it into the owned 308-byte
row-strided one-bit matrix at `+0x140`. `FUN_18005d9e0:0x18005da55..0x18005da83`
later clones `+0x140` for aggregate rescue. Record transformation follows at
`0x18004b671..0x18004b6a4`, and only then does `FUN_180037480` partition complete
56-byte records and publish `+0x118` at `0x18004b6a9`. Final mask generation and
record partitioning have no shared predicate, although the earlier optional
broken-pixel filter uses the live record count as its entry gate and may reduce
that count.

Anti-fake and rescue intentionally observe different owners. After extraction
returns, `FUN_1800392f0` reads feature `+0x20` from the object passed by
`identifyImage` at `0x180001dd3`, so anti-fake sees the pre-filter
half-resolution sample. Rescue
instead sees `+0x140`, which is derived from finalized inline `+0x28` after
mode-one clearing. `FUN_180040a70:0x180040bb3..0x180040bee` serializes only the
72-byte `+0x28` mask as tag `ce`; `FUN_18003d6c0:0x18003d7ec..0x18003d905`
copies that tag back to `+0x28` and regenerates `+0x140` through
`FUN_1800721a0` and `FUN_180073950`. The pre-filter `+0x20` matrix is neither the
serialized source nor the rescue source.

## Source Boundary And Failure Semantics

For valid extraction coverage `0..100`,
`goodix_match_extract_planes()` computes the type-12 limit as
`max(1, coverage * 150 / 100)`, yielding `1..150`; record materialization can
still return zero. Its mask ownership must remain split: the pre-filter
`feature_mask` is the anti-fake input, while `info->rescue_mask` must be packed
from `goodix_milan_feature_mask_expand(inline_mask, ...)` after every anti-fake
consumer has finished. Expanding before anti-fake would incorrectly expose
post-filter validity to `goodix_milan_antifake_build()` and, in debug builds,
`goodix_milan_antifake_build_with_boundary()`.

Map, extraction, anti-fake, tail, or pack failure frees all per-call owners,
publishes a null result, and returns `GOODIX_MILAN_EXTRACTION_INVALID`. The
classification state update intentionally precedes those fallible stages and is
not rolled back.

A zero-record feature can be packed because the record storage pointer remains
non-null and tag `b7` is zero, but it is not a complete match probe:
`milan_match_prepared_probe()` rejects `record_count == 0` at
`drivers/goodix53x5/milan/match/match.c:777-788`. This separates format
construction from matcher admission and avoids an empty partition dereference.
The source guard around `feature_filter_broken_pixels()` is also required for
native zero-count mask semantics: removing only that guard would clear mode-one
validity when global broken pixels reach 50, whereas the DLL returns before
computing the neighborhood plane. The allocated source record array is non-null;
independently, neither implementation dereferences record storage on its reached
zero-count path.

An order-discriminating low-quality control has an invalid alternating metadata
prefix: `FUN_18006fb10` returns zero, but `FUN_180048260` subsequently changes
the local to `512` (`high=2`, `low=0`) before the `+0x150` store. The value is
already `512` at the pre-anti-fake `identifyImage:0x180001dbd` boundary and
remains unchanged by both gallery matches. A native implementation that models
only the entry decoder therefore drops a real extraction-stage scalar.

## Match-Matrix Input Ownership

This function produces live feature count `+0xf0`, record pointer `+0xf8`, and
stored physical boundary `+0x118`, which are the complete feature-owned inputs
to later matrix production. It does not allocate or store either `180x180`
matrix. Feature masks, bitmaps, and active state are negative-control inputs to
the producer itself, although they can affect upstream record materialization.
