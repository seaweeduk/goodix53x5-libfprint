## Recovered Behavior

The function's first matrix argument is the normalized `104x88` image on the
profile-9/type-12 path. It allocates three one-byte temporaries at that geometry,
so each temporary is 9,152 bytes. It clears the first and third temporaries,
derives binary and enhanced/classification planes, and updates extraction-global
classification history.

The destination is different. `FUN_18004ae70` allocates feature `+0x158` from
the dimensions of feature matrix `+0x08`, which are `52x44` on this path:
exactly 2,288 bytes. Destination writes are mode-specific:

- Modes 3 and 4 project the enhanced `104x88` temporary to `52x44` by selecting
  even rows and even columns on the profile-9 projection path.
- Mode 5 requires the optional source pointer at configuration `+0x28`; when it
  is present, the destination is projected from that source. The projection
  selector at configuration `+0x20` chooses direct coordinates or even/even
  coordinates.
- Modes 0, 1, and 2 do not populate a destination plane. The final
  `FUN_180073fd0` call writes only bytes 0, 1, and 2 from the three local state
  words. Every byte from offset 3 through 2,287 remains prior allocator residue.

The fourth argument is an in/out packed-classification dword owned by
`FUN_18004ae70` and later stored as live feature `+0x150` / packed tag `c7`.
After current-frame and persistent-history classification, this function calls
`FUN_180073820` at `0x180048624` with the retained low class from configuration
`+0x10` and the final high class in `R14D`. The helper writes
`high_class * 0x100 + low_class` to the caller's dword. This is independent of
the mode-specific `+0x158` destination-plane projection.

A low-quality profile-9 control enters with entry metadata decode zero and exits
this function with high/low classes `2/0`, producing packed value `0x200`. The
extractor stores that value at feature `+0x150` before anti-fake construction.

## Component And History Planes

The scalar path uses three temporary `104x88` byte planes:

1. A current class plane starts at zero. A threshold plane is `0xff` where the
   first matrix is below `0x80`. `FUN_180047820` retains pixels in the three
   largest four-connected components strictly larger than 500 pixels; those
   pixels become current class 1.
2. The threshold plane is rebuilt as `0xff` where the first matrix is at least
   `0x80` and the second matrix is nonzero. The same component pass retains its
   three largest components; those pixels become current class 2.
3. A history-conditioned plane starts at zero. Once three retained planes are
   available, each `FUN_180047820` call requires the current component pixel to
   have the same class in all three retained planes, labels that stable mask,
   and writes the requested class for pixels in the three largest components
   strictly larger than 350 pixels. Class 1 is written first; class 2 only fills
   still-zero pixels.

The history-conditioned plane is then canonicalized: class 1 and class 2 pixels
are counted separately and both become byte 2; every other pixel becomes byte
1. These two counts drive the current class/mode seed:

- If stable class-1 count is above 600, seed 2 becomes 5, seed 1 becomes 4, and
  seed 0 becomes 3.
- When stable class-1 count is at most 600, stable class-2 count above 600
  promotes seed 0 to 3.
- If neither strict-600 promotion applies, either stable count above 300
  promotes seed 0 to 2.

The current class plane, not the canonicalized history-conditioned plane, is
what is appended to retained history. Its pixels are exactly 0, 1, or 2.

## Scalar State Machine

Let `current` be the promoted byte-0 seed, `high` the decoded entry high class,
`low` the decoded entry low class, and `aux2` auxiliary byte 2:

1. `high = max(high, current)`.
2. If `high < 2` and `aux2 > 0`, increment `high` once.
3. If auxiliary byte 1 is 2, replace `high` with
   `max(high, DAT_1801dc99c)`. Otherwise update `DAT_1801dc998`: increment it up
   to 5 when any of `high`, `current`, or `aux2` is above 1; decrement it when
   all three are below 2 and the counter is nonzero.
4. Store the merged `high` in `DAT_1801dc99c`.
5. If `DAT_1801dc998 >= 3`, clamp `high` to at least 1.
6. Call `FUN_180073820(packed_c7, low, high)`.

Thus the exact packer operands at `0x180048615..0x180048624` are
`EDX=config[+0x10]` and `R8D=R14D`, the final value after every transition
above. For the authoritative low-quality control they are exactly `low=0` and
`high=2`, producing `0x200`. No constant `0x200` exists in this path.

## Retained Globals And Ring Update

| Global | Exact role |
| --- | --- |
| `DAT_1801dc990` | retained plane count, saturated at 3 |
| `DAT_1801dc994` | last coverage written by a call whose auxiliary-byte-1 selector is not 2 |
| `DAT_1801dc998` | 0..5 high-class hysteresis counter |
| `DAT_1801dc99c` | previous merged high class |
| `DAT_1801ce3e0` | retained plane slot 0 |
| `DAT_1801d3070` | retained plane slot 1 |
| `DAT_1801d7d00` | retained plane slot 2 |

Each ring slot has generic stride `0x4c90`, although this call copies only the
current `104*88 = 9,152` bytes. There is no row-wise `108`-to-`104` remap at
this boundary: extraction consumes and replaces the contiguous 9,152-byte
prefix, while preprocessor import/export treats the retained plane as 9,504
profile-9 pixels. A call with coverage at least 75 appends when
the selector is not 2. With selector 2, append instead requires the retained
`DAT_1801dc994` coverage to be below 75. Counts 0..2 select the corresponding
slot. At count 3, slot 1 is copied to slot 0, slot 2 to slot 1, and the new
plane is copied to slot 2. The count then increments and saturates at 3.

The scalar is packed before this append. Current-call `c7` therefore observes
only the previously retained planes; its newly built current class plane can
affect extraction classification starting with a later call.

`DAT_1801dc990` and the three planes are shared with the profile-9 preprocessor
state packet: `FUN_1800501d0` can import them and `FUN_18004ff40` serializes
them. Serialization precedes this extraction append, so a newly appended plane
first appears in the workspace packet on the next preprocessor call.
`DAT_1801dc994`, `DAT_1801dc998`, and `DAT_1801dc99c` have no xrefs outside this
function and are neither imported nor serialized. No explicit reset writes any
of the four extraction globals or ring planes in the analyzed DLL. They begin
as zero-initialized BSS at DLL load; existing context-clear and preprocessor-exit
boundaries do not provide a per-identify reset.

The ordinary v3 probes select mode 0 and observe those first three bytes as
`00 00 00`. That proves the decoded auxiliary tuple, including the external
class later passed to candidate policy, is zero; it does not make the remainder
of the allocation defined.

## Linux Comparison And Implementation Boundary

The older profile-9 retained-reference fields still implement the earlier
preprocessor classifier represented by `FUN_1800508a0`, `FUN_1800512c0`, and
`FUN_18004f540`; they are not aliases for this extraction classifier:

- `profile9_history_count` is the capped-50 reference/support count, not the
  three-plane `DAT_1801dc990` ring count.
- `profile9_history_update_count` and `profile9_component_age[]` implement the
  capped-5 preprocessor component-age path, not `DAT_1801dc998` or the retained
  0/1/2 extraction planes.
- `profile9_class_counts` counts the preprocessor broken-level class plane. It
  does not contain the stable class-1/class-2 counts computed here from the two
  extraction matrices and three retained planes.
- `milan_profile9_update_history()`, `milan_profile9_component_class1()`, and
  `milan_profile9_temporal_class3()` operate on normalized reference/support or
  gradient-age state. None consumes the two feature-extraction matrices or
  reproduces `FUN_180047820`'s strict 500/350 component passes and three-frame
  retained-class unanimity.

Current source now owns the distinct state explicitly in
`GoodixMilanExtractionClassificationState`: three `88x104` class planes,
retained count, prior coverage, high-class hysteresis, and prior merged high
class. `goodix_match_update_extraction_classification()` matches the native
label limits, four-connectivity, strict 500/350 component floors, strict
600/300 promotions, three-plane unanimity, scalar merge, pack-before-append
order, coverage gate, ring shift, and count saturation.

The source call boundary is also correctly placed. `goodix_match_extract_planes()`
first builds the two `104x88` extraction inputs, decodes entry metadata, and
then updates `fields.optional_c7` and the persistent state before feature-record
materialization, anti-fake construction, tail construction, or template
packing. A failure in any of those later stages does not roll the classification
state back. The runtime owns a generation-state copy and marks it valid after
successful preprocessing; auth and enrollment publish that copy even when
later extraction returns retry. This reproduces the native commit timing while
giving the state a deliberate per-generation lifetime instead of the DLL's
unreset process globals.

Two source names require care:

- `primary_histogram_state` / `auxiliary[0]` seeds the extraction current
  class and the first `+0x158` summary byte. It is independent of
  `entry_low_class`, which is decoded from packed entry metadata and passes
  unchanged to the low byte of `c7`.
- `classification_mask` is the cropped retained primary-contrast plane, not a
  canonical boolean mask. This path only tests it for zero/nonzero while the
  selected processed crop supplies the `< 0x80` / `>= 0x80` split.

No required extraction-classification source correction was found in this
audit. Renaming those two operational concepts would be optional clarity only;
the current data flow and state ownership are exact.
