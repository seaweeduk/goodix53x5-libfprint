# FUN_18002d280

## Audit Scope

Production adapter caller of `enrolStartEx` at `0x1800010d0`. This note was
created before first Ghidra inspection during the independent methodology audit.

## Questions

- How are capacity, mode, required samples, and reserved values selected?

## Audit Findings

- Production creates a mode-0 session with `maximum=40`, requested count `0`,
  and reserved value `0`, then overwrites the session's requested-count field
  from the WBF enrollment requirement.
- The overwrite is a 16-bit store to session offset `+0x08` at
  `0x18002d3c7`: `*(int16_t *)(session + 8) = *required_samples`.
- Session `+0x08` is the required count; session `+0x0a` is the
  algorithm-maintained used count and `+0x0c` is progress. `FUN_18002eb80`
  reads them together at `0x18002ebdb..0x18002ec12`.
- The production `enrolStartEx` call is at `0x18002d309`; its arguments are
  exactly `(&maximum_40, 0, 0, 0)`. The returned session is published to
  global `0x18019b968` only after the `+0x08` count write.
- The `40` is allocation/session capacity, not required or used count. On the
  default path these begin as capacity `40`, required `12`, and used `0`.
- The oracle's `maximum=40, requested=8` call matches only a production
  requirement of 8, not the default requirement of 12, and still differs in
  initialization sequence. An exact production-path oracle should request zero
  and perform the same 16-bit `+0x08` write before the first `enrolAddImage`.
