## Partition And Matrix Contract

The enrolled and probe physical partitions are the stored half-open ranges
`[0,boundary)` and `[boundary,count)`. Their boundaries come from the respective
feature objects at `+0x118`; record class bytes do not define the boundaries.
Within each physical partition, the function collects class-1 and class-2
record indices, identified by record byte `+12`, in physical order and calls
`FUN_1800770e0` in both directions: enrolled class 1 against probe class 2, and
enrolled class 2 against probe class 1. No scan crosses a stored physical
boundary.

The function borrows two caller-owned `180x180` byte matrices. `FUN_18005a3c0`
initializes the eligibility/distance matrix to `0xff` and the layout matrix to
zero; `FUN_180078a70 -> FUN_180076400` fills only the two same-partition
rectangles. For each candidate pair, signed eligibility byte `-1` rejects the
pair. The layout byte selects probe tail offset 48 when zero and 40 otherwise;
the enrolled tail begins at offset 40. The selected eight-byte tails are
compared over two 32-bit words and admitted at Hamming distance at most profile
configuration word 5, which is 16 for profile 9/type 12. `FUN_180075220`
neither derives matrix decisions from the records nor mutates the matrices.

## Candidate And Selection Order

`FUN_1800770e0` stores best and second distances by original enrolled index.
Updates are strict: an equal best leaves the earlier probe as best and may
become second, while an equal second leaves the earlier second. The final
selector scan therefore publishes compact `(enrolled,probe)` pairs in enrolled
physical order. The two class directions have independent best/second arrays
and independent capacity-42 outputs. Empty class lists or physical partitions
contribute no candidates; their outputs are still padded with `-1,-1`.

`FUN_180075a60` owns ratio, spatial collision, replacement, pruning, capacity,
and sentinel semantics. Its post-replacement continuation is reachable here:
class-2 records with in-image, extractor-aligned Q8 coordinates and distances
within the profile-9 limit can present a replacement followed by both a later
equal-or-better collision and a still-later worse collision. The selector keeps
the replacement, continues past the equal-or-better collision, and may prune
the later worse collision. The retained natural profile-9 rows contain no
instance of this shape; that corpus absence does not make the state unreachable.

## Source Correspondence

The reviewed `origin/milan-dev` baseline and this documentation worktree have two
source divergences in `correspondence.c`: spatial collision sums are widened to
`int64_t`, and `milan_store_cross_class_match()` stops at an equal-or-better
collision even after an earlier replacement. The pending one-file production
patch, which is not merged into `milan-dev`, restores signed-dword spatial
arithmetic across the correspondence selectors and the cross-class
post-replacement continuation/pruning rule.

The native cross-class API also recomputes eligibility and layout from records
instead of accepting the two matrices. It is equivalent when the matrices are
canonically produced by `FUN_180076400`, but cannot represent a synthetic-valid
DLL call in which matrix eligibility or layout intentionally disagrees with the
records. That separate API limitation is not changed by the pending collision
patch.
