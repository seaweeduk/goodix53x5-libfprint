## Behavior

- Clamps every u16 input sample above `0x0fff` to `0x0fff`.
- Only packed chip types `0x10` and `0x12` apply `0x0fff - sample`. Production
  profile 9 / subtype 12 has packed chip type value `0x0c`, so canonical setup
  and live samples are not inverted. `preprocessor` constructs this selector
  from the initialized chip-info globals; the source descriptor's separate
  `0x10` format byte is not forwarded as this selector.
- For the profile-9 validated live path, calls `FUN_1800695e0`, then copies row
  1 to row 0, row `height - 2` to row `height - 1`, column 1 to column 0, and
  column `width - 2` to column `width - 1`. It does not replace invalid samples
  in row 1, row `height - 2`, column 1, or column `width - 2`.
- The nonvalidated setup path first replaces zero/`0x0fff` samples in those
  second-from-edge positions from the next interior sample, then copies the
  outer edge. Treating the two paths as equivalent caused the action-2 stage-1
  mismatch.
- Validation precedes every profile-9 live gain, classification, rendering, and
  quality operation in `FUN_18006d540`. Its ready input is independent of the
  exported identify/enrol purpose. A failure sets quality and coverage to zero,
  frees the copied raw frame, and returns immediately; setup content and
  retained generation state cannot turn the same raw frame into a success.
- At raw indices 3022 and 3454 (column 106 of width 108), Windows retains
  `0x0fff` and propagates it to column 107. Native had replaced those values
  from column 105 (`4073` and `4070`). Preserving the validated-path behavior
  makes the complete stage-1 calibration map byte-exact.

## Independent Retry-Retention Audit (2026-08-04)

- Ghidra confirms that validation failure returns `0x29aa` for the validated
  live selector and `0x29bb` for its sibling selector at
  `0x1800698e5..0x180069925`; neither return rolls back earlier generation-state
  writes in the caller.
- Direct chronology preserving the generation-use-7 `0x29aa` call makes use 8
  succeed with processed SHA-256
  `ca232ed53bc9e3020d5829d8920d3c75b3d5d704b3749cf4689335f8dbc09727`.
  This confirms that the `0x29aa` validation-retry call is a preprocessing
  prelude, not a fatal generation reset.
- This retained-state meaning does not make the rejected call a successful
  preprocessing result. A focused profile-9 first-live control returned
  `0x29aa` repeatedly with quality and coverage still zero and the
  caller-initialized 9,504-byte output still zero. Passing that descriptor to
  `identifyImage` returned `0x83` with a zero-record probe. The call is valid
  only as chronology retained for a later use; an oracle must not report it as
  a completed preprocessing/extraction lifecycle.
- Packed chip-type inversion at `0x18006986b..0x1800698e3` is selected only for
  values `0x10` and `0x12`. Profile 9's packed chip type is `0x0c`; despite the
  sensor subtype also being numbered 12, that inversion branch belongs to
  other sensors and must not be implemented for ours. Confidence is high.

## Targeted Input-Ordering Audit (2026-08-08)

- The raw input is first copied by `FUN_18006d540` at `0x18006d693..0x18006d6a4`.
  `FUN_180069820` then clamps all `width * height` copied samples at
  `0x18006984d..0x18006986b`, applies any chip-type inversion at
  `0x18006986b..0x1800698e3`, and only then enters live validation at
  `0x1800698e5`. Profile 9 does not select inversion, so its exact order is
  copy, whole-frame clamp, two-pixel-interior admission, then outer-border copy.
- Setup calls use the same whole-frame clamp before the nonvalidated border
  repair branch. Therefore neither setup nor live input is rejected merely
  because a u16 source sample exceeds `0x0fff`; it continues as `0x0fff`.
- Current Linux `goodix_milan_preprocess()` instead runs raw admission first and
  then returns generic failure if any setup or live sample exceeds `0x0fff`.
  Admission itself remains equivalent for an over-range interior live sample,
  because native clamps it to `0x0fff` and the strict `< 0x0ed8` test excludes
  it. The later all-frame rejection is not equivalent: an otherwise admissible
  live frame, an over-range border-only live frame, or any over-range setup
  frame must proceed with clamped samples.
- The confirmed corpus does not distinguish these behaviors. This is a required
  production correction, not an optional naming or defensive-contract change.
