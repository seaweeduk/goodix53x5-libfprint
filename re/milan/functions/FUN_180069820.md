## Behavior

- Clamps every u16 input sample above `0x0fff` to `0x0fff`.
- Only packed chip types `0x10` and `0x12` apply `0x0fff - sample`. Production
  profile 9 / subtype 12 has packed chip type value `0x0c`, so canonical setup
  and live samples are not inverted. `preprocessor` constructs this selector
  from the initialized chip-info globals; the source descriptor's separate
  `0x10` format byte is not forwarded as this selector.
- For the profile-9 validated live path, calls `FUN_1800695e0`, then copies row
  1 to row 0, row `height - 2` to row `height - 1`, column 1 to column 0, and
  column `width - 2` to column `width - 1`. It does not replace invalid samples
  in row 1, row `height - 2`, column 1, or column `width - 2`.
- The nonvalidated setup path first replaces zero/`0x0fff` samples in those
  second-from-edge positions from the next interior sample, then copies the
  outer edge. Treating the two paths as equivalent caused the action-2 stage-1
  mismatch.
- At raw indices 3022 and 3454 (column 106 of width 108), Windows retains
  `0x0fff` and propagates it to column 107. Native had replaced those values
  from column 105 (`4073` and `4070`). Preserving the validated-path behavior
  makes the complete stage-1 calibration map byte-exact.
